# 認証は最後に切り替え、再ログインで未送信記録を消さない

状態：未実施の手順案。前提は[認証設計](auth-design.md)と[メール設計](email-design.md)の合格。
業務API/DB・メディア・ジョブがSupabase Authを検証する期間を経て、短い停止枠で認証だけ切り替える。

## 通常ログアウトと移行による再認証を分ける

現在のAuthContextは `SIGNED_OUT` で計画の端末控えと入力フォーム草稿を清掃する。
保存済みの調査/私有スポット待ち行列とIndexedDB圏外記録は、このイベントだけでは消さない。
移行時の失効で入力草稿を失わず、保持済みキューも誤送信しないよう、それぞれの保存先を検証する。
切替前に移行対応クライアントを配布し、`active / migration-reauth-required / frozen / signed-out` の状態を分ける。
移行による失効ではキュー・下書きを元UIDに紐づけて凍結し、同じUIDの再認証後だけ再送する。
別UIDのログイン時は前利用者の内容を表示/送信しない。本人による破棄は確認操作に限る。
端末へ暗号化しない機密情報を新しく増やすものではない。既存の保持/清掃契約を踏まえ実装する。

古いSW/タブは旧 `SIGNED_OUT` で入力草稿等を清掃し得る。移行前から保持と更新導線を配り、更新条件を定める。
未更新クライアントのデータ保護を保証できない場合はAuth切替を延期する。単に旧APIを閉じて解決済みとはしない。
停止時の401/更新要求を通常ログアウトへ短絡させず、送信失敗でも記録が残ることを実端末で試す。
根拠：[AuthContext](../../../src/context/AuthContext.tsx)、[offlineSend](../../../src/lib/offlineSend.ts)、
[私有キュー](../../../src/features/fieldwork/lib/queue.ts)。

## 移行前のリハーサル

| 照合対象 | 合格条件 |
| --- | --- |
| 利用者とidentity | UUID・登録日時・確認状態・Google provider/subject・ban・役割が一致。重複を勝手に統合しない |
| パスワード | 旧hashの正常/異常入力、Unicode/長文、回復後の旧password拒否、並行認証とCPUを試験 |
| session | 通常失効・全端末失効・退会・降格がSSR/API/管理画面へ反映される |
| OAuthとメール | 旧/新callback・再送・期限切れ・先読み・途中失敗・メール変更を管理下の環境で試験 |
| 端末保存 | 未送信あり/圏外/別タブ/別UID/旧SWで、切替→再認証→再送または本人破棄を実操作 |
| 復元 | Auth表・権限・鍵と業務参照を隔離復元し、失効済み/削除済みを有効化しない |

hashや旧tokenを含む移行素材は承認した暗号化保管先で扱い、短い保持期限と削除記録を設ける。
本番のMFA/ban/重複/未確認数・Google client・SMTP・hash costは今回未照合であり、P0で台帳化する。

## 切替当日

1. 対象版・schema・配信枠・管理者の回復経路・復元証拠・停止枠を確認する。
2. 旧Authの登録・password/email変更・連携・退会を止め、進行中の操作が無いことを確認する。
3. auth.users/identities等の最終差分を取り込み、既存の確認状態と権限、参照を全件照合する。
4. Web/APIの認証先と宛先参照を切り替え、旧refresh/sessionを新sessionへ変換せず全員を再認証へ送る。
5. 古いJWTを業務APIが拒否することを確認し、旧直アクセス/Edgeの残存経路も閉じる。
6. 新登録・確認・Google・回復・管理・退会と同一UIDでの未送信再送を確認して再開する。
7. 失敗率・メール遅延・認証CPU・抑止・未送信残数を監視する。旧認証データは規定期間保持する。

旧確認/回復tokenと進行中OAuthは新基盤へ移植しない。既存 `/auth/callback` で新手順の再送/やり直しへ案内する。
旧のtokenを新handlerへ転送して認証させず、リンクに秘密を付けたままログ・計測へ流さない。
旧SDKのCookie/端末tokenを消す処理と、観察記録を保持する処理を分ける。

## 認証を戻すときは、資格情報の変更も戻す必要がある

新認証で書込みを始める前なら旧Authへ戻せるが、セッション失効済みなら再ログインが必要となる。
新認証を再開した後は、新登録・password/email変更・ban/role・連携解除・退会を保護された変更台帳で追跡する。
回復tokenや平文passwordは台帳へ保存しない。状態と必要な暗号化済み資格情報の逆移行可否を事前検証する。
旧Authへ表現できないhash/identity/失効を含む場合は、古い資格情報を再有効化せず、新認証側で復旧する。
特に変更前password・退会済み利用者・解除済みGoogle連携・降格前の管理者権限を復活させてはならない。
新Authへの変更、送信済みメール、配信停止と抑止、削除差分を照合してから読書きを再開する。
一般の[切替手順](cutover-and-rollback.md)の差分復旧に、この認証固有の条件を加える。

## Supabase Authを廃止できる条件

ブラウザ/SSR/API/全ジョブからSupabase Auth/管理APIへの呼出が無く、旧JWTを受け付ける経路が無い。
メール宛先・役割・退会・未送信の照合と復元が成立し、旧リンク/旧クライアントの案内保持期間が決まっている。
安定監視後に旧Authの保管/削除対象を提示する。DB・Storage・Edgeの廃止条件も満たしてから解約を判断する。
