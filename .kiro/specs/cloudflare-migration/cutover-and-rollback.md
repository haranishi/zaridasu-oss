# 書込みの停止と差分照合を切替の条件にする

状態：本番切替用の手順案。Web候補と合成DBのlocal検証を実施中で、切替操作は行わない。
現段階の再現手順とremote配備の保留条件は[Cloudflare preview手順](../../../docs/runbooks/cloudflare-preview.md)へ。
本番実施前に担当・停止枠・RPO/RTO・復旧上限・証拠の保存先を記入し、手順をリハーサルする。

## 公開前に隔離環境で通す検証

| 対象 | 合格の条件・残す証拠 |
| --- | --- |
| 既存品質 | lint・型・i18n・schema・秘密・単体・E2E・容量・DB/Edgeの対象検査が成功 |
| workerd | ビルドだけでなく実ランタイムでページ・SSR・API・Cookie/Proxy・例外監視が動く |
| 権限 | 匿名/本人/他人/管理者/内部処理の許可と拒否、所有者変更・審査値偽装・NULL拒否を試験 |
| 公開経路 | 地図・CSV/GeoJSON・OGP・集計・画像/CDNで非公開データと正確座標が漏れない |
| ログイン | メール・Google OAuth・回復・Cookie更新・ログアウト・退会と未送信確認が成功 |
| メディア | 公開/非公開の4種で、旧URL、新URL、期限切れ、別人、削除失敗の再試行を検証 |
| データ | 表別件数・ID集合・正規化ハッシュ・FK・公開投影、メディア全件の内容ハッシュが一致 |
| 競合/再送 | 二重審査・並行投稿/上限・削除競合・再送・タイムアウト後の照会で整合性を保つ |
| 非同期 | AI/通知/cronの新旧起動元、重複抑止、再試行、失敗隔離、再実行を試験 |
| PWA/地図 | SW更新、IndexedDB下書き、回線復帰再送、別アカウント、Wasm fallbackを実操作 |
| 配信 | 静的/動的のCSP・no-store・MIME、ISR期限/再検証、画像origin限定が成立 |
| 外部設定 | DNS・TLS・メール認証・OAuth戻り先・Turnstile・Sentry環境分離を確認 |
| 性能/費用 | 同条件の現行比較、p50/p95・失敗率・CPU・DB往復・従量実績が確定した予算/閾値内 |
| 復元 | 隔離復元後、ログイン境界・公開投影・非公開写真・削除状態を確認しRPO/RTOを実測 |

認証切替には[認証固有の手順](auth-cutover.md)、メールには[配信/停止/抑止](email-design.md)の条件も加える。
[障害台帳](migration-blockers.md)のP0と[全14処理](background-processing.md)の代替が、対象段階で解消済みであること。

既存SQLの権限テストは、そのままSQLiteへ実行できない。要件ごとにAPI/DB試験との対応を作る。
本番で初めて付くホスト名・TLS・ヘッダー・秘密設定も、previewで同条件を作って確認する。
実データの写真・希少種位置・メール・鍵をCIのログやArtifactsへ置かない。

## Web切替：書込み先は変えない

1. 対象commit・旧Vercel配備版・DNS・担当・停止枠・復旧上限を記録。選択済みアカウントの隔離previewで公開前検証を通す。
2. SupabaseのDB/Auth/Storage/Edgeを同じ正本として維持し、OAuth/Turnstile等の許可先を準備する。
   noindex・送信停止だけを閲覧認証と扱わず、previewの公開範囲とアクセス制限も確認する。
3. 低トラフィック枠で配信を切り替え、HTTP・認証・公開閲覧・Sentry・p95を確認する。
4. 不合格なら配信先を記録済みVercel版へ戻す。DBは同じなのでDB逆移行は不要。Cookie/セッション・cache・未送信キューを確認する。

localの26件合格だけで切り替えない。remote plan/起動時間・IMAGES/R2/DO・zone画像source制限、
未訪問の遅延chunkと下書き/再認証を含むoffline、現行Vercelとの実比較を対象commitで確認する。

## メディア/DB切替：全書込み元を止める

1. 初回コピーと隔離リハーサルを完了し、移行元を正本として維持する。
2. UIだけでなく旧Data API・Storage upload・Edge・cron・管理操作・遅延ジョブの書込みを止める。
3. 停止完了を確認し、キューを排出/停止して最終差分コピーと全照合を実行する。
4. 変換エラー・件数/ハッシュ不一致・権限漏れ・復元失敗が1件でも残れば切替を中止する。
5. 新API/メディア/DBの読取り、正本への書込み、Outbox消費を切替単位で合わせ、段階的に再開する。
6. 業務更新と同じtransactionで変更台帳を確定する。逆変換に必要な値・順序・versionと削除記録を残す。
7. 再開後は投稿/審査/削除/通知/認証と監視値を照合し、旧経路への書込みが0であることを確認する。

台帳はアプリログと分離して認可・暗号化・保持期限を設ける。受理後のクラッシュでも差分が失われないことを試す。
R2は実体保存後に参照と台帳を確定し、削除は削除記録を先に確定する。未確定アップロードを受理済みとしない。

オフライン端末は停止を知らずに旧経路へ送ることがある。旧APIで拒否/更新案内を返す設計と保持期間が要る。
停止による未送信は端末へ残し、移行完了を理由に下書きを消さない。

## 書込み開始前と開始後で切り戻しを変える

**新保存先で書込みを始める前**なら、移行元のデータを変更せず読書き経路・旧ジョブを復旧する。
部分移植中に新旧ジョブが同じ副作用を送らないよう、起動元と再開位置を確認する。

**新保存先で書込みを始めた後**は、DNSや接続文字列だけを戻すと更新を失う。
まず全書込みと副作用を止め、変更台帳から追加・更新・削除・送信済み状態を取り出す。
事前に試験した逆変換で旧DB/R2参照へ反映し、件数・ID・ハッシュ・削除・Outbox状態を再照合する。
認証IDと参照先も整合してから旧経路を再開する。写真の新規作成と削除も逆同期の対象に含む。
逆変換/復元が未検証、または新データを表現できない場合は旧経路を再開せず、停止状態で復旧する。

目標は切替時の受理済み記録の損失0。一般障害のRPO/RTOは別に合意し、バックアップだけで損失0を保証しない。
旧環境の削除は安定監視・復元・保管期限の確認後に別判断とする。
