### REQ-004: 写真削除の不整合修正（orphan ファイル防止）

**背景**
`useDeletePost.js` では Storage 削除 → DB 削除の順で処理しているが、Storage 削除が失敗しても DB 削除は実行される。また、`usePostForm.js` で複数写真のアップロード中に一部が失敗した場合、成功済みの写真が Storage に残ったまま（orphan ファイル）になる。

#### ユーザーストーリー

```
As a サービス管理者,
I want to Storage の孤立ファイルが発生しない仕組みにしたい,
So that ストレージコストを抑え、データの整合性を維持できる。

受け入れ条件:
- [ ] 投稿削除時に Storage 削除が失敗した場合、DB 削除もロールバックされる（またはリトライされる）
- [ ] アップロード途中で失敗した場合、成功済みの写真も削除される
- [ ] Storage 削除失敗時のエラーをユーザーと管理者ログに記録する
- [ ] 孤立ファイルを定期的に検出・削除するジョブを用意する
```

#### 機能要件

| # | 要件 | 優先度 |
|---|------|--------|
| F1 | `useDeletePost.js` で Storage 削除失敗時にユーザーへ通知し、DB削除を中止するオプションを実装 | 高 |
| F2 | `usePostForm.js` の `uploadPhotos()` でアップロード失敗時に成功済みファイルをロールバック削除する | 高 |
| F3 | Supabase Edge Function または Cron Job で孤立ファイルを定期検出する仕組みを設計する | 中 |
| F4 | `audit_logs` テーブルに削除失敗イベントを記録する | 低 |

#### フロー設計

```
投稿削除フロー（改善後）:
  1. Storage から写真を削除
     ├─ 成功 → DB から投稿を削除 → 完了
     └─ 失敗 → ユーザーへ通知（「写真の削除に失敗しましたが、投稿は削除しますか？」）
               ├─ はい → DB削除実行（孤立ファイルは後続ジョブで処理）
               └─ いいえ → 操作を中止

アップロード失敗フロー（改善後）:
  1. photos[] を並列アップロード
     ├─ 全成功 → 投稿を DB に保存
     └─ 一部失敗 → 成功済みの写真を Storage から削除（ロールバック）
                   → ユーザーへ「写真のアップロードに失敗しました。再度お試しください。」
```
