# スパム対策強化 要件定義

## 1. 概要
- 対象課題: 匿名投稿スパムへの耐性不足
- 優先度: 高
- 作成日: 2026-03-14

## 2. 背景
クライアント側の事前制御は UX には有効だが、防御としては不十分。サーバー側での IP ベース制限、継続的な自動フラグ、監査可能性を強化する必要がある。

## 3. 目的
- 短時間連投をサーバー側で確実に抑止する
- 通報多発ユーザー投稿を早期に検知する

## 4. スコープ
### 対象
- 投稿 API（Edge Function 経由）
- DB レート制限トリガー
- 通報連動フラグ付け

### 非対象
- CAPTCHA 導入
- 外部 WAF 導入

## 5. ユーザーストーリー
As a サービス管理者,
I want to スパム投稿をサーバー側で自動抑止したい,
So that データ品質と運用負荷を改善できる。

## 6. 受け入れ条件
- [ ] 匿名ユーザーは IP 単位で 1 分 3 件、24 時間 10 件を超えると拒否される
- [ ] 認証ユーザーは 24 時間 5 件制限を維持する
- [ ] ブロック時に次回投稿可能時刻が返却される
- [ ] 管理者は制限対象外
- [ ] 通報 3 件以上で投稿に自動フラグが立つ

## 7. 機能要件
| ID | 要件 | 優先度 |
|---|---|---|
| F1 | `posts` に投稿元 IP 保持用カラムを追加する（非公開） | 高 |
| F2 | 投稿作成を Edge Function 経由に統一し、IP を安全に取得して DB に渡す | 高 |
| F3 | レート制限トリガーを IP ベース条件に拡張する | 高 |
| F4 | 制限エラーに次回許可時刻を含める | 中 |
| F5 | reports 数閾値超過時に `is_flagged` を自動更新する | 中 |

## 8. 非機能要件
- IP は 90 日保持後に削除する
- 投稿判定の追加処理による遅延は 200ms 以内
- 個人情報保護方針に沿って取り扱う

## 9. 実装方針
- 投稿処理の入口を一本化し、クライアント直 insert を避ける
- DB 側で最終判定し、クライアントは補助表示に留める

## 10. テスト観点
- 匿名連投の拒否
- 認証ユーザー制限維持
- 管理者除外
- 通報閾値による自動フラグ

## 11. 完了定義
- スパム制限が DB/Function 双方で有効
- レート制限の回帰テストが通る
- 運用ログで拒否件数を追跡可能
