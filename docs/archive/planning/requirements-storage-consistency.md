# ストレージ整合性改善 要件定義

## 1. 概要
- 対象課題: 投稿削除/アップロード失敗時の orphan ファイル
- 優先度: 高
- 作成日: 2026-03-14

## 2. 背景
写真の削除と DB 削除、複数写真アップロードで部分失敗時のロールバックが不十分な場合、ストレージに孤立ファイルが残る。コスト増加と整合性低下を招くため、失敗時の一貫した復旧動作が必要。

## 3. 目的
- Storage と DB の整合性を保つ
- 失敗時にユーザーと運用側が状況を把握できるようにする

## 4. スコープ
### 対象
- 投稿削除フロー
- 複数写真アップロードフロー
- 孤立ファイル検出ジョブ

### 非対象
- 画像圧縮アルゴリズム変更
- ストレージプロバイダ変更

## 5. ユーザーストーリー
As a サービス管理者,
I want to 失敗時でも Storage と DB の整合を保ちたい,
So that 孤立ファイルを防ぎ運用コストを抑えられる。

## 6. 受け入れ条件
- [ ] 写真削除失敗時は DB 削除を停止、またはユーザー確認付きで継続できる
- [ ] 複数写真で 1 枚でも失敗したら成功済みアップロードをロールバック削除する
- [ ] 失敗時のユーザー通知が明確である
- [ ] 孤立ファイルを定期検出する仕組みがある

## 7. 機能要件
| ID | 要件 | 優先度 |
|---|---|---|
| F1 | `useDeletePost` で Storage 削除失敗時の分岐（中止/確認継続）を実装する | 高 |
| F2 | `usePostForm` のアップロードを成功パス追跡方式に変更する | 高 |
| F3 | 途中失敗時に成功済みファイルを remove するロールバック関数を導入する | 高 |
| F4 | 失敗イベントを監査ログに記録する | 中 |
| F5 | 定期ジョブで orphan ファイルを検出・削除する | 中 |

## 8. 非機能要件
- 失敗時のユーザー待機時間を最小化する
- ロールバック成功率 100% を目標とする
- 削除処理の再実行性を担保する

## 9. 実装方針
- 逐次アップロードで進捗管理を明確化
- DB 反映前に Storage 成功を必須化
- 例外時は必ず後始末を実行

## 10. テスト観点
- 全成功
- 部分失敗とロールバック
- 削除失敗時の分岐
- 孤立検出ジョブの検知精度

## 11. 完了定義
- 孤立ファイル発生が新規に確認されない
- 削除/アップロード失敗系テストが green
- 運用ログで失敗追跡可能
