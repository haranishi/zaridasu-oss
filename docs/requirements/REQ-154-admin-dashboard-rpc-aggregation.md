# REQ-154: 管理ダッシュボードのデータ取得が複数クエリ＋クライアント集計で非効率

## 背景
管理ダッシュボードは `src/hooks/useAdminStats.ts` の `useAdminStats` フックで統計データを取得・集計している。日付レンジ（`range`）に応じて投稿件数・前期比・未対応通報数・実名投稿数・種別/情報種別/月次/市区町村の集計・最近の投稿・監査ログをまとめて取得し、画面に渡す。

## 現状の問題
`useAdminStats.ts:88-108` で **7 本のクエリを `Promise.all` で並列実行**し、そのうち集計系（種別・情報種別・月次・市区町村ランキング）は **全件の生データをクライアントに取得してから JS でループ集計**している。

実際のクエリ構成（`Promise.all` の配列、`:96-108`）:
1. `filteredPosts('id', true)` — レンジ内総件数（count のみ、`useAdminStats.ts:97`）
2. `prevPosts('id', true)` — 前期総件数（count のみ、`:98`）
3. `reports` の未解決件数 `count`（`resolved=false`、`:99`）
4. `filteredPosts('id', true).eq('is_anonymous', false)` — 実名投稿件数 `count`（`:100`）
5. `filteredPosts('species, info_type, municipality, created_at')` — **レンジ内の全投稿行を取得**（`:101`）
6. `recentPosts` — 最近の投稿（`QUERY_LIMITS.recentPosts` 件、`:102-106`）
7. `supabase.rpc('get_audit_logs', { p_limit: 5, p_offset: 0 })` — 監査ログ（`:107`）

クライアント側集計（`:112-149`）:
- 種別カウント `speciesCounts`（`:116-118`、`rows.forEach`）
- 情報種別カウント `infoTypeCounts`（`:121-123`、`rows.forEach`）
- 月次集計 `monthly`（`:125-138`、月ごとに `rows.filter` を回す）
- 市区町村ランキング `municipalityRanking`（`:141-149`、`rows.forEach` + `Object.entries().sort()`）

問題点:
- クエリ5は集計のためだけにレンジ内**全投稿の `species/info_type/municipality/created_at` 行を転送**しており、投稿が増えるほど egress とクライアント集計コストが線形に増大する。本来 DB 側で `GROUP BY` 可能な集計をアプリ層に持ち込んでいる。
- `Promise.all`（`:96`）は1本でも reject すると全体が失敗し `catch`（`:164-170`）に落ちる。監査ログ RPC や個別 count が失敗しただけで、集計可能だった他指標まで含めてダッシュボード全体が「統計データの取得に失敗しました。」になる。
- クエリ1・4・5は同一レンジ・同一テーブルに対する重複アクセスであり、count とデータ取得が分離している。

## 目的
集計処理を DB 側の RPC（`GROUP BY` による集約）に寄せ、クライアントへ転送する行数とクライアント集計コストを削減する。あわせて取得を `Promise.allSettled` 化し、一部クエリの失敗が他指標の表示を巻き込んで全滅させないようにする。

## 要件
### 機能要件
- [ ] FR-154-01: 種別カウント・情報種別カウント・月次集計・市区町村ランキングを DB 側で集約する RPC（例: `get_admin_post_stats(p_from, p_to)`）を新設し、レンジ内全行転送（`useAdminStats.ts:101` の `filteredPosts('species, info_type, municipality, created_at')`）を廃止する。RPC は集約済みの結果（種別別件数・情報種別別件数・月次件数・市区町村別件数）を返す。
- [ ] FR-154-02: 月次集計（`:125-138`）は RPC 側で `date_trunc('month', created_at)` 等により集約し、現在クライアントで行っている月ごとの `rows.filter` ループを撤廃する。`QUERY_LIMITS.adminMaxMonths` 相当の上限はサーバ／クライアントいずれかで一貫して適用する。
- [ ] FR-154-03: 取得処理を `Promise.all`（`:96`）から `Promise.allSettled` に変更し、各クエリの成否を個別に評価する。成功した指標は表示し、失敗した指標のみ既定値（0 / 空配列）でフォールバックする。
- [ ] FR-154-04: フォールバック時は `error` を即全画面エラーにせず、致命的（主要指標がすべて取得失敗）な場合のみ `setError(...)` する。部分失敗は `logError` でログに残す。
- [ ] FR-154-05: 既存の `AbortController`／`abortSignal`（`:57-58`, `:72`, `:99-107`, `:110`, `:165`, `:173`）と `range` 依存（`:174`）の挙動を維持する。RPC 呼び出しにも `abortSignal` を付与する。
- [ ] FR-154-06: 新設 RPC には適切な権限・RLS 整合性（管理者のみ実行可能、または既存の管理者判定経路と一致）を持たせる。

### 非機能要件（該当する場合）
- [ ] NFR-154-01: レンジ内投稿が多数（例: 数千件以上）でも、ダッシュボードへ転送される行数が件数に比例せず、集約済み件数（種別数・月数・市区町村数オーダー）に収まること。
- [ ] NFR-154-02: ダッシュボード初期表示の取得・集計時間が現状比で改善すること。

## 受入条件
- [ ] AC-01: 管理ダッシュボードの総件数・前期比・未対応通報・実名投稿数・種別/情報種別/月次/市区町村ランキング・最近の投稿・監査ログが、現状と同じ値で表示される。
- [ ] AC-02: レンジ内全投稿行を取得していたクエリ（旧 `:101`）が RPC 集約に置き換わり、クライアント側の `rows.forEach`／`rows.filter` 集計（`:116-149`）が撤廃または最小化されている。
- [ ] AC-03: いずれか1本のクエリ（例: 監査ログ RPC）を意図的に失敗させても、他の集計指標が引き続き表示される（`Promise.allSettled` による部分失敗耐性）。
- [ ] AC-04: `next build` および型チェックがエラーなく完了する。

## 影響範囲
- `src/hooks/useAdminStats.ts`（取得構成 `:88-108`、クライアント集計 `:112-149`、エラーハンドリング `:164-170`）
- Supabase 側 DB マイグレーション（新規 RPC 関数の追加・権限設定）
- 管理ダッシュボード画面（`useAdminStats` を利用する管理ページ）

## 優先度
- **緊急度**: 中 / **重要度**: 高 / **理由**: 現状でも動作するが、集計用に全行を転送する設計はデータ増加に対してスケールせず egress とクライアント負荷が線形に増大する。また `Promise.all` の全滅特性により、軽微なクエリ失敗で管理画面全体が使えなくなる運用リスクがある。
