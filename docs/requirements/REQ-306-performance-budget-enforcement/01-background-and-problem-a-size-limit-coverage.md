### 問題A: size-limit の予算が実際の配信量の約 3% しかゲートしていない — High

`.size-limit.json:1-50` の 8 エントリのうち、共有チャンクを見ているのは `Framework + React chunk`（`4bd1b696-*.js`、60 kB）の 1 本だけ。残り 7 本は `app/**/page-*.js` かオプトインの `crayfish3d*.js` を指す。

結果として、**/ (home) の 332.2 kB のうち監視されているのは 9.3 kB（2.8%）にすぎない**。REQ-305 の問題A（Sentry SDK 49.0 kB gzip が全ルート常駐）も、新たな共有チャンクの肥大も、**`npx size-limit` は全項目グリーンのまま通過する**。

さらに `/dashboard`（347.1 kB＝**最も重いルート**）と `/ranking`（305.3 kB）には**そもそも予算エントリが存在しない**。ルート固有チャンクの肥大すら検知されない。

**共有チャンク個別エントリの落とし穴**: 共有チャンク名（`9898` / `6962` / `5653` / `4600` / `5662`）は webpack の採番であり、**モジュール構成が変わると番号自体が変動する**。`9898-*.js` のようにハッシュだけをワイルドカード化した glob を書いても、番号が変われば **「対象ファイル 0 件」で size-limit はエラーにならず通過する（＝検知漏れが静かに発生する）**。したがって個別エントリは補助にとどめ、**主たるゲートは「ルート単位の First Load JS 合計」で持つ**必要がある。この合算は `.next/app-build-manifest.json` の各ルートのファイル一覧を gzip 圧縮して足すだけで求まり、本監査の実測値はまさにこの方法で得ている（＝**実装可能性は実証済み**）。
