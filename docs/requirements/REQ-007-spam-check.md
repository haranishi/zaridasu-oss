# REQ-007: クライアントサイドスパムチェックのバイパス防止

## 背景

投稿フォーム（`usePostForm.ts`）にはスパム防止のためのレートリミット機能が実装されているが、クライアントサイドで `localStorage` に投稿タイムスタンプを保存する方式であり、ブラウザの開発者ツールから容易にバイパス可能である。DBレベルではレートリミットトリガー（`check_post_rate_limit`）が存在するが、クライアント側チェックとDB側チェックの間に閾値や対象の不整合がある。

## 現状の問題

### クライアント側レートリミット（`src/hooks/usePostForm.ts`）

- **L135-154 `checkSpamLimit()` 関数**: `localStorage` の `zarigani_submit_timestamps` キーに投稿タイムスタンプ配列をJSON形式で保存し、24時間以内の投稿数をチェックしている。
- **L139**: `localStorage.getItem(SPAM_KEY)` でタイムスタンプを取得 - ユーザーはブラウザの開発者ツールで `localStorage.removeItem('zarigani_submit_timestamps')` を実行するだけでリミットをリセットできる。
- **L146**: 閾値は `SPAM_LIMIT_POSTS = 5`（`constants.ts:171`）、ウィンドウは `SPAM_LIMIT_WINDOW_MS = 24時間`（`constants.ts:172`）。
- **L136**: `isAdmin` の場合はチェックをスキップしているが、この判定もクライアント側で行われている。

### DBレベルレートリミット（`supabase/schema.sql`）

- **L86-119 `check_post_rate_limit()` トリガー**: サーバーサイドで投稿レートを制限している。
- **L98-103**: 認証ユーザー（`user_id IS NOT NULL`）の場合、24時間以内に5件の制限。クライアント側と同じ閾値。
- **L105-109**: 匿名ユーザー（`user_id IS NULL`）の場合、1分以内に3件の制限。ただし現在のRLSポリシー（`schema.sql:417-419`）は `auth_insert` ポリシーにより認証ユーザーのみINSERT可としているため、匿名投稿パスは実質的に無効。

### 不整合・問題点

1. **バイパス容易性**: `localStorage` はユーザーが自由に操作可能。シークレットウィンドウを使うだけでもリセットされる。
2. **UXの不整合**: クライアント側チェックをバイパスしてDBトリガーでエラーが返った場合、エラーメッセージがPostgreSQLの例外メッセージ（日本語）になり、UIのエラーハンドリングが適切でない可能性がある。
3. **匿名チェック不在**: クライアント側の `checkSpamLimit()` は認証ユーザーを前提としているが、DBトリガーの匿名ユーザー用チェック（L105-109）に対応するクライアント側ロジックがない（ただし現在は匿名投稿が無効のため顕在化していない）。

## 目的

クライアントサイドのスパムチェックはUX目的のみとし、セキュリティ上のレートリミットはDB側トリガーに一本化する。クライアント側はDB側エラーを適切にハンドリングする。

## 要件

### 機能要件

- [ ] FR-007-01: クライアント側の `checkSpamLimit()` はUXフィードバック目的であることを明確化するコードコメントを追加し、セキュリティ境界ではないことを明記する。
- [ ] FR-007-02: DBトリガー `check_post_rate_limit()` のエラーメッセージ（`'24時間以内の投稿上限（5件）に達しました'`）がSupabaseクライアント経由で返された場合に、`submitPost()` のcatchブロック（L236-245）で適切にパースし、ユーザーフレンドリーなエラーメッセージを表示する。
- [ ] FR-007-03: DBトリガーの認証ユーザー用レートリミット（24時間5件）とクライアント側の閾値（`SPAM_LIMIT_POSTS = 5`, `SPAM_LIMIT_WINDOW_MS = 24h`）を定数として一元管理し、不整合を防止する。

### 非機能要件

- [ ] NFR-007-01: レートリミットのセキュリティ境界はあくまでDBトリガーであり、クライアント側チェックが無効化されてもシステムの安全性は維持されること。
- [ ] NFR-007-02: DBトリガーのレートリミットエラー時のレスポンス時間が通常のエラーレスポンスと同等（500ms以内）であること。

## 受入条件

- [ ] AC-01: `localStorage` の `zarigani_submit_timestamps` を削除してから5件以上投稿を試みた場合、6件目でDBトリガーによるエラーが返り、UIに適切なエラーメッセージが表示されること。
- [ ] AC-02: DBトリガーによるレートリミットエラーが発生した場合、`submitPost()` が `false` を返し、`error` ステートに日本語のユーザーフレンドリーなメッセージが設定されること。
- [ ] AC-03: クライアント側の `checkSpamLimit()` 関数のJSDocまたはコメントに「UX目的のみ、セキュリティ境界ではない」旨が明記されていること。

## 影響範囲

- `src/hooks/usePostForm.ts` （L135-154: コメント追加、L236-245: エラーハンドリング改善）
- `src/lib/constants.ts` （L171-173: 定数のドキュメント追加）
- `supabase/schema.sql` （L86-119: 必要に応じてエラーメッセージの統一）

## 優先度

- **緊急度**: Medium
- **重要度**: High
- **理由**: DBレベルのレートリミットトリガーが既に存在するため、即座の攻撃リスクは限定的。ただしクライアント側チェックをバイパスした場合のUX（エラーメッセージ）が不適切な可能性があり、DBトリガーエラーの適切なハンドリングは信頼性向上のために重要。
