## 目的

- シークレット漏洩・アカウント乗っ取り・課金異常・個人データ漏洩・サービス障害の各インシデントについて、**一人でも「考えず読んで動ける」初動 runbook を `docs/` 配下に整備する**。
- 全 runbook に共通の初動順序（記録 → 証拠保全 → 封じ込め → 影響範囲特定 → 一次連絡 → 通報・相談 → 復旧 → 再発防止）を貫き、「**緊急時ほど削除を急ぐと証拠を失う**」という原則を明文化する。
- 個人データ漏洩について、**個人情報保護委員会への報告 / 本人通知の判断材料**（トリガと期限の目安。数値は最新要確認）をザリダスの保持データに紐づけて用意する。
- Obsidian 既存 runbook 群（`07/23/27/13` 他）との**リンク運用**を定め、汎用知見（Obsidian）と PF 固有手順（リポジトリ）の二層を維持する。

### 非機能要件（該当する場合のみ）

- [ ] NFR-220-01: **秘密値・PII を runbook に書かない。** 識別はメタデータ（プロバイダ名・資格情報種別・所有者・末尾数文字・キー ID 等）で行う（`23_Leak_Response_Playbook` の冒頭原則に準拠）。runbook 自体・スクリーンショット・チケットに秘密値や実ユーザーの個人データを残さない旨を明記する。
- [ ] NFR-220-02: **オフライン可用性。** 事故時は本番・各種ダッシュボードが使えない / パニック状態になり得るため、runbook は Markdown 単体で完結し（外部レンダリング前提にしない）、印刷 / オフライン閲覧でも初動チェックリストと連絡先が読める構成にする（`07_Incident_Response`「安全な運用方法」の「いつでも開ける場所に」に準拠）。
- [ ] NFR-220-03: **最新性の担保。** 法令の数値（報告期限・閾値）・各社 UI / 復旧フォーム URL は変わり得るため、runbook 内の該当箇所に「**要確認**」マーカーと「確認日」を付け、半期ごと等の見直しタイミングを README に記す。
- [ ] NFR-220-04: **コード非干渉。** 本 REQ の成果物はドキュメント（`docs/` 配下の Markdown）のみで、アプリ本体・Supabase スキーマ・CI を変更しない。
