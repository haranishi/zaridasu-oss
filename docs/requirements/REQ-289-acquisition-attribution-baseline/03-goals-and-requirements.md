## 目的

1. 施策を開始する前に、流入元を**分離して計測できる器**を用意する
2. 2026-08-02 のベースラインを実測値として確定・記録する
3. 表記ゆれによる集計不能を防ぐ
4. 計測の検証手段（本番限定という制約下での）を確立する

## 要件

### 機能要件

- [ ] **FR-289-01**: `src/lib/shareUtm.ts` に `utm_content` を追加する。オプション引数とし、未指定なら従来どおり付与しない（既存の呼び出し元の挙動を変えない）。
- [ ] **FR-289-02**: 外部施策向けの計測 URL を生成するユーティリティを追加する。`utm_source` / `utm_medium` / `utm_campaign` / `utm_content` と `from` を一貫した規則で組み立てられること。マーケ担当（＝本人）が手作業で URL を組まなくて済む形にする。
- [ ] **FR-289-03**: `from` の値を台帳化する。少なくとも次の施策を識別できる値を定義する:
  - [ ] ゲームからの送客（`zarigani-game` の `zaridasu.com` リンク）
  - [ ] Instagram（プロフィールリンク / ストーリーズ / 投稿別）
  - [ ] A4 チラシの QR コード
  - [ ] 名刺
  - [ ] LP（既存の `lp`）
  - [ ] 大学・ゼミ経由
- [ ] **FR-289-04**: 台帳に無い `from` 値を受け取った場合の扱いを決めて実装する。**推奨は「`other` へ丸めたうえで元の値も別プロパティで送る」**。丸めることで集計軸が汚れず、元値を残すことで台帳追加漏れに後から気づける。
- [ ] **FR-289-05**: メール登録経路で `from` が失われる問題（§C）に対応する。最低限、**失われることを前提とした集計方法を文書化**する。実装で対応する場合は、確認メールのリダイレクト URL に `from` を引き継ぐ（`sessionStorage` に依存しない）方式を検討する。
- [ ] **FR-289-06**: `/lp` へのアプリ内導線を実装する（REQ-176 FR-176-12 / REQ-206 FR-206-08）。ただし **REQ-284 の紹介ストーリーと役割が重複する**ため、着手前に「LP へ送るのか、アプリ内ストーリーを見せるのか」を決めること。
- [ ] **FR-289-07**: 2026-08-02 時点のベースラインを確定し記録する。記録先は `docs/` 配下（KPI 文書）と Obsidian の両方。少なくとも次を含む: 認証済み登録者数・投稿数・承認済み投稿数・週次アクティブ投稿者数（WAC）・流入元別セッション（GA4）。
- [ ] **FR-289-08**: 計測の検証手順を `docs/runbooks/` に追加する。本番でしか発火しない制約（§D）を明記し、本番で安全に検証する方法（自分のセッションを除外する / GA4 の DebugView を使う 等）を記述する。
