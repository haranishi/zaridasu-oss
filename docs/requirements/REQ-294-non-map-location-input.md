# REQ-294: 地図に依存しない位置入力手段の追加（キーボード・支援技術での投稿到達性）

作成日: 2026-07-30
優先度: **P0** ／ 深刻度: **Critical** ／ 種別: アクセシビリティ（中核機能のブロック）
状態: **✅ 実装済み（2026-07-30。FR-294-03 の地名検索は提供元未決定のため対象外／AC-02 のスクリーンリーダー実機完走は未検証）**
関連: REQ-202（地図マーカーのキーボード a11y）, REQ-283（フィールド探索モード・未実装）, REQ-172（GPS 精度バッジ）, REQ-255（対象県外のソフト警告）, REQ-144（react-leaflet の動的 import）

## 概要

**本アプリの中核機能である「投稿」は、現在マウス／タッチで地図をクリックできる利用者しか完了できない。** 位置は必須項目であり、その唯一の入力手段が地図の `click` イベントであるため、キーボードのみの利用者・スクリーンリーダー利用者は送信まで到達できない。WCAG 2.1 の **2.1.1 キーボード（レベル A）** の失敗であり、市民参加型の観測データ収集サービスとして、特定の利用者を投稿から完全に排除している状態である。

## 背景

### 問題A: 位置の入力手段が地図クリックのみで、キーボード操作では確定できない — Critical

- `src/components/features/posts/LocationPicker.tsx:20-22` は位置確定の経路として `useMapEvents({ click(e) { setPosition(e.latlng) } })` **のみ**を持つ。Leaflet の標準キーボード操作（矢印キーによるパン、`+` / `-` によるズーム）は地図をパン・ズームするだけで `click` を発火しないため、キーボードだけでは何度操作してもマーカーを置けない。
- `src/components/features/posts/LocationSection.tsx:105-113` は `MapContainer` ＋ `TileLayer` ＋ `LocationPicker` のみで構成され、**緯度経度の数値入力・「現在地を使う」ボタン・住所/地名検索のいずれも存在しない**。地図の下に表示されるのは確定済み座標のテキスト（`:114-124`）と未選択時の案内文（`:126-135`）だけで、代替入力への導線がない。
- `MapContainer`（`LocationSection.tsx:105-109`）には `aria-label` も操作説明もなく、支援技術には「何のための領域か」「どう操作するか」が一切伝わらない。
- `src/components/features/posts/PostForm.tsx:179` が `if (!position) { setPositionError(t('postForm.locationError')); return }` で送信をブロックするため、**位置未設定のままではフォームを送信できない**。すなわち位置入力が不能であることは、そのまま投稿フォーム全体の到達不能を意味する。

### 問題B: 自動 geolocation は救済策として成立していない — High

`PostForm.tsx:151-168` はマウント時に一度だけ `navigator.geolocation.getCurrentPosition` を呼ぶが、次の4点により救済範囲が極端に狭い。

1. **マウント時1回のみ**（`useEffect(..., [])`）。ユーザーが後から権限を許可しても再取得されない。
2. **`AKITA_BOUNDS` 外の結果を破棄する**（`:156-162`）。秋田県外にいる利用者（県外からの調査依頼者・自宅で下書きする利用者など）は座標が得られても位置が入らない。
3. **失敗時のハンドラが `() => { /* 位置取得失敗は無視 — ユーザーは地図で手動選択可能 */ }`**（`:164`）。理由の提示も再試行 UI もない。コメントが前提としている「地図で手動選択」自体が問題A で不能なため、この設計判断の前提が崩れている。
4. **`{ timeout: 5000 }`**（`:166`）。低速測位環境では黙って失敗する。

結果として自動取得が効くのは「位置情報を許可済み」かつ「物理的に秋田県内」の場合のみで、**GPS を拒否した端末・県外の利用者・GPS を持たないデスクトップでは常に位置未設定**になる。

### 問題C: 調査依頼フォームは同じ地図を使い、フォールバックすら無い — Critical

- `src/components/modals/SurveyRequestForm.tsx:145-148` は同じ `LocationPicker` を使うため、問題A をそのまま継承する。
- さらに `MapContainer` に **`zoomControl={false}`** が指定されており（`:145`）、マウス利用者向けのズームボタンさえ存在しない。
- **geolocation による自動取得のフォールバックが実装されていない**（`PostForm.tsx:151-168` に相当するコードがない）。
- `SurveyRequestForm.tsx:82` の `if (!position) { setError(t('survey.errors.noPosition')); return }` で送信がブロックされるため、調査依頼も同じくキーボード／支援技術のみでは送信不能である。

### 波及: REQ-283（フィールド探索モード）

REQ-283 は現地スキャンから投稿への接続を新規に設計するが、位置入力に同じ `LocationPicker` を前提とすると同じ壁を新機能側にも作ることになる。本要件で導入する非地図入力を、REQ-283 の位置入力の前提として先に整えること。

## 機能要件

- **FR-294-01**: `LocationSection` に**非地図の位置入力**を併設する。最低限、緯度・経度の数値入力（`<label htmlFor>` と `id` を紐付けたフォームコントロール）を提供し、入力値の形式・範囲を検証して `setPosition` に反映する。秋田県外の座標は**入力段階では破棄せず保持して理由を提示する**（`role="status"` のソフト警告）。

  > ⚠️ **2026-07-30 決定（当初記述の訂正）**: 本FRは当初「送信はブロックしない」と書いていたが、これは誤り。`akitaLatLngSchema`（`src/lib/validation/schemas.ts`）と DB CHECK が `AKITA_BOUNDS` 外をハードに拒否する設計は**維持する**。理由は3点。①ザリダスは秋田県の分布データを収集する研究基盤で、県外座標の混入はデータ品質を直接損なう ②zod を緩めると DB CHECK・オフラインキュー・公開データセットまで波及する ③**本REQのCritical課題（キーボード・支援技術で位置を設定できない）は、秋田県内の座標を手入力できるようになった時点で解消しており、県外座標の送信可否とは独立**。したがって FR-294-01/02 が要求するのは「県外座標を**黙って捨てない**（保持して理由を説明する）」ことのみで、送信の許可ではない。REQ-255 のソフト警告も表示方針の話であって制約の緩和ではない。
- **FR-294-02**: 「現在地を使う」ボタンをキーボード到達可能な要素として**画面上に明示配置**する。押下ごとに geolocation を再取得し、失敗時は理由（権限拒否／タイムアウト／未対応）を提示して**再試行できる**ようにする。`AKITA_BOUNDS` 外の結果は破棄せず、FR-294-01 と同じソフト警告扱いにする（＝保持して理由を出す。送信可否は FR-294-01 の決定に従い変更しない）。
- **FR-294-03**: 住所／地名によるテキスト検索から座標を決定できる手段を提供する。**採用する順方向ジオコーディング手段（提供元・利用規約・コスト・レート制限）は着手時に決定する（要確認）。** 既存の `useReverseGeocode` は逆方向のみで転用できない。実現性の判断が付くまでの間も、FR-294-01・FR-294-02 だけで「地図を使わずに投稿を完了できる」状態は成立させること（FR-294-03 は本要件の完了条件から切り離してよい）。
- **FR-294-04**: 地図側にもキーボード経路を追加する。`MapContainer` に `aria-label` と操作説明（キーボードでの操作方法を含む可視テキスト）を与え、フォーカスされた地図上で **Enter / Space により現在の地図中心（クロスヘア位置）を確定**できるようにする。確定した座標は支援技術にも通知する。
- **FR-294-05**: `SurveyRequestForm` にも FR-294-01〜04 と同じ入力手段を適用する。`LocationSection` 相当を共有コンポーネント化して両フォームから使うことを基本とし、`zoomControl={false}` を撤去してズームボタンを復帰させる。
- **FR-294-06**: 追加する UI 文言（ラベル・ボタン名・エラー文・操作説明）はすべて `t()` 経由とし、ja/en/ko/zh の4言語にキーを追加する。**`aria-label` に日本語リテラルを直書きしない**（REQ-304 と同方針）。

## 非機能要件

- **NFR-294-01**: 非地図入力の追加によって Leaflet の初期ロード条件を変えない（REQ-144 の遅延 chunk 化を維持し、地図を開かずに位置入力だけを行う経路では leaflet を読み込まないことが望ましい）。
- **NFR-294-02**: 既存の GPS 精度バッジ（REQ-172、`LocationSection.tsx:59-88`）の意味を壊さない。手動で緯度経度を入力した場合は `locationSource='manual'`／`accuracy=null` を維持し、GPS 由来のときのみ精度を送る現行仕様（`PostForm.tsx:193-195`）を保つ。

## 受入基準

- **AC-01（本要件の中心）**: **マウス・タッチ・トラックパッドを一切使わず、キーボード操作のみで投稿フォームを開いてから送信完了まで到達できる。** 地図をクリックしない経路で位置が設定できることを操作手順として記録する。
- **AC-02**: スクリーンリーダー（VoiceOver または NVDA のいずれか1つ以上）で、位置の設定から送信完了までを完走できる。位置が確定したことが読み上げで確認できる。
- **AC-03**: 位置情報の権限をブロックした状態、かつ**利用者の物理現在地が秋田県外**の環境（デスクトップを含む）でも、秋田県内の座標を手入力して位置を設定し投稿できる。県外座標そのものは保持され理由が表示されるが、送信は既存の `akitaLatLngSchema` / DB CHECK により拒否される（FR-294-01 の決定どおり。これは仕様であり不具合ではない）。
- **AC-04**: 調査依頼フォーム（`SurveyRequestForm`）でも AC-01〜AC-03 が成立する。ズームボタンが表示される。
- **AC-05**: 「現在地を使う」の失敗時に、失敗理由と再試行手段が画面に表示される（無言で終わらない）。
- **AC-06**: 追加した i18n キーが ja/en/ko/zh 4言語すべてに存在し `npm run i18n:check` がパスする。
- **AC-07**: `PostForm.a11y.test.tsx` / `SurveyRequestForm.a11y.test.tsx` の axe 検査に critical 違反がなく、非地図入力のラベル関連付けを検証するテストが追加されている。
- **AC-08**: `lint` / `type-check` / 既存652テストがパスする。

- `LocationPicker.tsx` — Enter / Space による地図中心の確定
- `SurveyRequestForm` の `zoomControl` を復帰
- bbox 判定を `isWithinTargetBBox`（包含・非有限値ガード付き）へ統一（`PostForm` の自動GPS判定と `usePostForm` の EXIF GPS判定。REQ-314 で指摘した「排他/包含の不一致で境界ちょうどの座標がGPS自動入力だけ弾かれる」問題も同時に解消）

### 実装レビューで検出・修正した欠陥
`<MapContainer aria-label={...}>` は **DOM に一切出力されていなかった**。react-leaflet 5.0.0 の `MapContainer` は div へ `className` / `id` / `style` のみを spread し、残りの props は `new LeafletMap(node, options)` に渡されて Leaflet が黙って捨てる。JSX ではハイフン入り属性名が props 型と照合されないため `tsc` も検出しない。実測すると `aria-label` が `null` である一方 Leaflet が `tabindex="0"` を付けており、**名前のない要素にフォーカスが入る**状態だった。

修正は `useMapEvents` 経由で得た Map インスタンスの `map.getContainer()` に `aria-label` / `aria-describedby` を設定し、cleanup で削除する形。**モックしない実 react-leaflet を jsdom で render する回帰テスト**（`LocationPicker.integration.test.tsx`）を追加して DOM 属性を直接検証している。既存のモック版テスト（`LocationPicker.test.tsx`）が Enter/Space を検証していてもこの欠陥を見逃した事実が、統合テストを必須にした根拠。

### 既知の挙動変更（REQ-255 との関係）
`PostForm.tsx` の県外バナー表示条件が `outsideTargetArea && position && isWithinTargetBBox(...)` になり、**bbox 外の座標では REQ-255 のバナーが出ない**（代わりに `ManualLocationInput` 側の警告が出る＝警告の二重表示を回避）。意図は妥当だが REQ-255 の挙動変更として認識しておく。
