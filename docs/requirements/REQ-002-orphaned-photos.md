# REQ-002: バリデーション失敗時の孤立写真（Orphaned Photos）問題

## 背景
投稿フォーム送信時、写真のアップロードとフォームデータのバリデーションの実行順序に問題があり、バリデーション失敗時にSupabase Storageに不要な写真ファイルが残留する。

## 現状の問題
- `src/hooks/usePostForm.ts:175-198` — `submitPost()` 関数の処理順序:
  1. **177行目**: 写真がある場合、先に `uploadPhotos()` を実行（Supabase Storageにアップロード完了）
  2. **184-188行目**: その後に緯度・経度の範囲チェック（秋田県外ならエラー → `return false`）
  3. **190-193行目**: その後にコメント長チェック（500文字超ならエラー → `return false`）
  4. **194-198行目**: その後に個体数チェック（範囲外ならエラー → `return false`）

### 問題のフロー
```
submitPost() 開始
  ├─ photos あり → uploadPhotos() 実行 → Storage にファイル保存完了
  ├─ lat/lng バリデーション失敗 → return false
  │   └─ Storage の写真は削除されない（孤立）
  ├─ comment バリデーション失敗 → return false
  │   └─ Storage の写真は削除されない（孤立）
  └─ count バリデーション失敗 → return false
      └─ Storage の写真は削除されない（孤立）
```

### 影響
- バリデーション失敗のたびにStorageに不要ファイルが蓄積される
- ストレージコストが不必要に増加する
- 孤立ファイルの手動クリーンアップが必要になる
- `uploadPhotos()` 内のロールバック処理（104-113行目）は「アップロード途中のエラー」のみ対応しており、アップロード成功後のバリデーション失敗には対応していない

## 目的
バリデーションを写真アップロードの前に実行し、バリデーション失敗時にStorageへの不要な書き込みを防止する。

## 要件

### 機能要件
- [ ] FR-002-01: `submitPost()` 内のバリデーション（lat/lng、comment、count）を `uploadPhotos()` の呼び出しより前に移動する
- [ ] FR-002-02: バリデーションには共通関数 `validatePost()` を使用する（REQ-001と連携）
- [ ] FR-002-03: 万が一アップロード後にDB INSERT が失敗した場合のロールバック処理を追加する（アップロード済み写真の削除）

### 非機能要件
- [ ] NFR-002-01: バリデーション失敗時にStorageへの書き込みが一切発生しないこと
- [ ] NFR-002-02: 既存のアップロードロールバック処理（uploadPhotos内の104-113行目）はそのまま維持すること

## 受入条件
- [ ] AC-01: 秋田県外の座標で写真付き投稿を試み、バリデーションエラーが表示されること。かつ、Supabase Storageに写真が保存されていないこと
- [ ] AC-02: 501文字のコメントで写真付き投稿を試み、バリデーションエラーが表示されること。かつ、Supabase Storageに写真が保存されていないこと
- [ ] AC-03: 有効なデータで写真付き投稿を行い、正常に投稿・写真保存されること（既存動作を破壊しないこと）
- [ ] AC-04: DB INSERT 失敗時にアップロード済み写真が削除されること

## 影響範囲
- `src/hooks/usePostForm.ts` — `submitPost()` 関数の処理順序変更
- `src/lib/postValidation.ts` — 変更なし（バリデーション関数を呼び出す側の変更のみ）

## 優先度
- **緊急度**: Medium
- **重要度**: High
- **理由**: データ損失はないが、Storageに不要ファイルが蓄積し続ける。ユーザーが写真付き投稿でバリデーションエラーを繰り返す度に孤立ファイルが増加するため、運用コストに影響する。
