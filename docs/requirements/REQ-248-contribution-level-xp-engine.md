# REQ-248: 貢献レベル／経験値（XP）エンジン（品質連動・DB 権威・段階的機能解放の土台）

## 背景
ザリダスにはバッジ（`badge_definitions`/`user_badges`）・3 軸ランキング（多様性/品質/リーダーボード）・プロフィール実績があるが、**数値レベル・経験値・アンロックという「ゲームの進行」概念は一切存在しない**（`xp`/`level`/`unlock`/`tier` の grep が 0 ヒット＝グリーンフィールド）。ユーザーは「投稿するほど機能が段階的に解放される」体験を求めている。本 REQ は、その進行の**土台となる貢献レベル／経験値エンジン**を定義する。以降の「段階的機能解放（REQ-249）」「コレクション/図鑑/水槽（REQ-250）」「進捗演出/通知（REQ-251）」はすべてこのエンジンの出力（レベル・XP）を参照する。

**設計の最重要原則（Goodhart 対策・市民科学ファースト）**: 既存コードは「量ではなく検証済み品質を称える」思想を DB・RPC・要件（REQ-235）で明確に持つ。バッジ付与トリガー `check_and_grant_badges()` は `pending→approved` 遷移でのみ発火し、未承認/却下投稿は決して報酬にならない（`schema.sql:993`）。**進行エンジンもこの原則を厳守**し、XP は「承認済み（検証済み）投稿」と「品質シグナル」から算出する。生の投稿数・いいね数で XP を与えない。

> ⚠️ 既存の潜在ホール: ダッシュボードのクライアント側バッジ `BADGES`（`src/lib/constants.ts:245-250`、🥉1/🥈5/🥇10/🏆30）は `stats.myTotal`＝**ステータス無関係の全投稿数**（`src/hooks/useStats.ts:120`、RLS で本人は pending/rejected も見える）で駆動しており、**未検証投稿を数えてしまう**。本エンジン導入時にこれを検証済みベースへ是正する。

## 現状の問題（機会）
（ファイルパス:行番号つき）

1. **進行の骨格が無い**: レベル/XP/アンロックが存在しないため、「投稿するほど解放される」体験を実装する基盤が無い（grep 実証・グリーンフィールド）。
2. **品質シグナルは揃っているのに進行に未接続**: `posts` の `status`（`schema.sql:738-746`）・`auto_approved`・`ai_result.confidence`・`survey_method='structured'`・`accuracy`、多様性（species 2種 `constants.ts:117-121` / info_type 5種 `:157-163` / municipality 25 `:175-181`）は `get_user_quality`（`schema.sql:1153-1210`）・`get_user_diversity`（`:1121-1148`）で既に集計済み。これらを XP に束ねる層が無い。
3. **既存バッジと二重管理のリスク**: DB バッジ（承認ベース）とクライアント `BADGES`（myTotal ベース）が二重で、進行の「正」が曖昧。単一の DB 権威エンジンに寄せる必要がある。

## 目的
承認済み投稿と品質シグナルから算出する、改竄不能（DB 権威）な貢献レベル／XP エンジンを新設する。これを唯一の進行の正とし、バッジ・ランキング・機能解放・コレクションが一貫して参照できるようにする。量・いいね偏重に流れないアンチ Goodhart 設計を DB 側で強制する。

## 要件

### 機能要件
- [ ] FR-248-01: **XP 算出ルール（品質連動）**をサーバー（DB 関数）で定義する。承認遷移（`pending→approved`）を起点に、少なくとも以下を加点する。倍率/係数は運用調整可能な定数化:
  - 基本: 承認済み投稿 1 件 = 基本 XP。
  - 品質ボーナス: `auto_approved=true AND ai_result.confidence≥0.9`（高精度同定）／`survey_method='structured'`（定点観察・REQ-174）／`accuracy≤30`（GPS 良好・REQ-172）。
  - 多様性ボーナス（初回発見）: 新しい species / info_type / municipality の**初観察**に上乗せ（図鑑＝REQ-250 の種になる）。
  - `info_type='absence'`（不在確認＝価値ある負データ）にも加点。
  - **加点しない**: 下書き/pending/rejected、いいね受領、（原則）コメント。
- [ ] FR-248-02: **ファーミング抑止（アンチ Goodhart）**: 同一メッシュ/近接座標での反復観察は逓減、1 日あたり XP 上限、短時間大量投稿の減衰等を入れ、「量産で XP を稼ぐ」動機を作らない。REQ-212（レート制限）・REQ-173（空間バイアス nudge）と整合。
- [ ] FR-248-03: **レベル曲線**を定義する（単調増加のしきい値表。低レベルは軽く、上位は重い）。レベルは REQ-249 の機能解放・REQ-250 の水槽容量にマップする。曲線は定数（`constants.ts` など単一ソース）で管理し 4 言語 i18n のラベルを持つ。
- [ ] FR-248-04: **DB 権威・改竄不能**にする。XP/レベルは `SECURITY DEFINER` トリガー（`check_and_grant_badges()` と同じ承認遷移フック、`schema.sql:992-1048` の隣）で更新し、クライアントから書き込めない（`user_badges` と同じ「INSERT ポリシー無し＝トリガーのみ」パターン、`schema.sql:1575-1583`）。保存先は新テーブル `user_progress`（`user_id`, `xp`, `level`, `updated_at` 等）。
- [ ] FR-248-05: **参照 RPC** `get_user_progress(p_user_id)` を追加（`SECURITY DEFINER STABLE SET search_path=public`、集計のみ・生 PII を返さない、`is_public` 準拠）。既存 `get_user_quality`/`get_user_diversity` と同居させる。
- [ ] FR-248-06: **既存の是正**: ダッシュボードのクライアント側バッジ/進捗表示を検証済み（承認）ベースへ切り替える。`BADGES`×`myTotal`（未検証を数える）を、承認済み数＋本エンジンのレベルに置き換えるか併記で是正する。既存 DB バッジ（`posts_*`/`verified_25` 等）は後方互換で維持（消えない）。
- [ ] FR-248-07: **i18n**: レベル名・XP 文言を 4 言語（`src/locales/{ja,en,ko,zh}/translation.json`）に追加し `i18n:check` を通す。文言はブランドの穏やかな声（です・ます、「！」不使用、`docs/brand/brand-memo.md`）に従い、**「大学」「卒業研究」等の禁止語を使わない**。

### 非機能要件
- [ ] NFR-248-01: XP 更新は承認処理（AI 自動承認・管理承認）に対して**非干渉**（性能・失敗時のロールバックが投稿承認本体を壊さない）。既存トリガー群と整合。
- [ ] NFR-248-02: `user_progress` の RLS は本人＋（`is_public` 時）公開読み取り、書き込みはトリガーのみ。`schema:check`・pgTAP で改竄不能を検証。
- [ ] NFR-248-03: レベル/XP の再計算（係数変更時のバックフィル）手順を用意し、既存ユーザーのレベルが遡って算出できること。
- [ ] NFR-248-04: 追加集計 RPC は件数上限・インデックスを考慮し、`/ranking`・`/dashboard` の性能バジェット（REQ-124/191）を悪化させない。

## 受入条件
- [ ] AC-01: 投稿が承認されると XP が加算され、しきい値を超えるとレベルが上がる（pgTAP/手順で確認）。pending/rejected では加算されない。
- [ ] AC-02: 品質シグナル（高精度同定・定点・GPS 良好・初観察）に応じたボーナスが反映される。
- [ ] AC-03: 同一地点の反復量産では XP が逓減/上限に達し、量産インセンティブが働かない。
- [ ] AC-04: XP/レベルはクライアントから改竄できない（直接 UPDATE が RLS で拒否される）。
- [ ] AC-05: ダッシュボードの進捗表示が検証済みベースになり、`myTotal`（未検証）主導でなくなる。既存バッジに回帰が無い。
- [ ] AC-06: レベル/XP 文言が 4 言語に存在し `i18n:check` が通る。禁止語を含まない。

## 優先度
- **緊急度**: Low / **重要度**: Medium〜High
- **理由**: 機能不全ではないが、ユーザー要望である「投稿で段階解放される」体験の**必須土台**。品質シグナル・承認トリガー・バッジ基盤が既に揃っており追加コストが小さい。量・いいね偏重に流れる前に、DB 権威の品質連動進行を確立する価値が高い（卒研のデータ品質と継続動機を同時に押し上げる）。REQ-249〜251 の前提。
