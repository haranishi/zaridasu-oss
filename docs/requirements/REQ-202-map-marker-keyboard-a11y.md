# REQ-202: 地図マーカーのキーボードアクセシビリティ（無名タブストップの解消）

## 背景
ザリダスの地図ビュー `src/components/features/map/MapView.tsx` は Leaflet（react-leaflet）でマーカーを描画する。投稿マーカー（295行）と調査依頼マーカー（342行）は、Leaflet のデフォルト設定 `keyboard: true` により各マーカー DOM に `tabindex="0"` が付与され、キーボードのフォーカス対象（タブストップ）になる。

しかしマーカーのアイコンは `L.divIcon` による生 SVG（HTML 文字列）であり（定義は 44行=種別アイコン・71行=調査依頼アイコン・83行=不在確認アイコン）、その HTML には**ロールも accessible name もない**。結果として、投稿数が増えると最大数百件規模の「無名のタブストップ」が生成される。キーボード利用者は `Tab` のたびに何の情報も読み上げられないフォーカス対象を延々と通過させられ、`Enter` でポップアップは開くものの「何のボタンか」が分からない。

これは WCAG 2.1 の以下に該当する:
- **4.1.2 名前・役割・値（レベル A）**: フォーカス可能で操作可能な要素にロール・名前が必要。
- **2.4.3 フォーカス順序（レベル A）**: 大量の無名フォーカス対象はフォーカス順序を著しく劣化させる。

重要な前提: 地図上のデータには**代替経路が既に存在する**。`PhotoGallery`（写真ギャラリー、`src/app/(home)/HomeInteractive.tsx` のパネル切替で表示）が、マーカーと同じ投稿データへのキーボードアクセス可能な一覧を提供している。したがって「マーカー自体を完全アクセシブルにする」か「マーカーをタブ順序から外し、代替経路に委ねる」かの二択が成立する。

## 現状の問題
- `src/components/features/map/MapView.tsx:289-345` — `MarkerClusterGroup` 内の投稿 `<Marker>`（295行）と、クラスター外の調査依頼 `<Marker>`（342行）。いずれも Leaflet デフォルト `keyboard:true` で `tabindex=0` が付く。
- `src/components/features/map/MapView.tsx:44` / `71` / `83` — `L.divIcon({ html: svg, ... })` の SVG（`html` ルート）に `role` も `aria-label` もない。→ フォーカスは当たるが名前・ロールが読み上げられない。
- 投稿件数に比例してタブストップが増え、最大数百件の「無名タブストップ」となる。`Enter` でポップアップ（300行/347行）は開くが、フォーカス時点で内容が判別不能。

## 目的
地図マーカーのキーボード利用体験を WCAG レベル A に適合させる。具体的には、マーカーに意味のあるロール・名前を与えて操作可能にするか、代替経路（PhotoGallery）の存在を根拠にタブ順序から除外して「無名タブストップのノイズ」を解消するかのいずれかを採用する。

## 要件
### 機能要件
本要件は二者択一であり、実装時に **(A) / (B) のどちらかを採用**してその旨を記録する。判断基準は FR-202-03 に従う。

- [ ] FR-202-01（案 A: マーカーをアクセシブル化・推奨）: `L.divIcon` の `html`（44行=種別、71行=調査依頼、必要なら 83行=不在確認）のルート SVG（または SVG を包むラッパー要素）に `role="button"` と、種名・日付等を含む `aria-label` を埋め込む。
  - `aria-label` の文言は `t()` で**4 ロケール対応**とする（例: 「{種名} の{情報種別}・{日付}」）。投稿マーカーは `species` / `info_type` / `created_at`、調査依頼マーカーは種別 / 緊急度等から生成する。
  - `divIcon` の `html` は文字列のため、`t()` で得た文言を HTML エスケープしたうえで埋め込む（XSS 回避）。アイコン生成のキャッシュ（`speciesIconCache` 38行付近 / `surveyIconCache` 61行付近）は `aria-label` がマーカーごとに異なるため、キャッシュキーに名前要素を含めるか、`aria-label` だけ生成後に DOM へ付与する方式に見直す。
- [ ] FR-202-02（案 B: タブ順序から除外）: 代替経路（PhotoGallery）の存在を根拠に、`<Marker>`（295行・342行）に `keyboardable`/`keyboard: false` 相当の設定を明示し（react-leaflet では `<Marker keyboard={false}>`）、`tabindex` が付かないようにしてタブノイズを除去する。マウス/タッチでの操作は維持される。
  - 採用時は、地図データへのキーボード代替（PhotoGallery）が常に利用可能であることをコメント/ドキュメントで明示する。
- [ ] FR-202-03（判断基準）: 次を踏まえて A/B を選択する:
  - 「マーカーから直接ポップアップ→詳細へ遷移する」操作をキーボード利用者にも提供したい場合は **A**。
  - 数百件規模でフォーカス順序のノイズ除去を最優先し、PhotoGallery で十分にデータ到達可能と判断する場合は **B**。
  - 採用案・判断理由を本書または PR 説明に記録する。
- [ ] FR-202-04: 採用案に応じて、不在確認アイコン（83行）・調査依頼アイコン（71行）も同方針で統一する（A なら名前付与、B なら同マーカーも `keyboard={false}`）。

### 非機能要件（該当する場合のみ）
- [ ] NFR-202-01（案 A 採用時）: マーカー数が多い状況でも、`aria-label` 生成・アイコンキャッシュ変更による描画パフォーマンス劣化が体感できない範囲に収まること（既存のクラスタリング/チャンク読み込みを阻害しない）。
- [ ] NFR-202-02（案 A 採用時）: `divIcon` の HTML へ動的文言を埋め込む際、ユーザー由来データ（種名は固定だが将来拡張に備え）を必ずエスケープし、XSS を作り込まないこと。

## 受入条件
- [ ] AC-01（案 A 採用時）: 地図上のマーカーへフォーカスすると、スクリーンリーダーが「ボタン」＋種名・日付等の名前を読み上げる。axe で対象マーカー要素に `button-name` 違反が出ない。
- [ ] AC-02（案 B 採用時）: 地図上のマーカーがタブ順序に含まれず（`tabindex` が付かない）、`Tab` でマーカー群を通過しない。PhotoGallery 経由で同データへキーボード到達できることを E2E で確認する。
- [ ] AC-03: 採用案にかかわらず、マウス/タッチでのマーカー操作（ポップアップ表示・詳細遷移）が従来どおり動作する。
- [ ] AC-04: 地図を含むページに対する axe 検査でマーカー起因のランドマーク/名前違反が増えない（A では解消、B では対象外化）。
- [ ] AC-05: 既存の地図・投稿表示関連テスト（あれば E2E 含む）が全て成功する。

## 影響範囲
- `src/components/features/map/MapView.tsx`（38〜58行: 種別アイコン生成、61〜80行: 調査依頼アイコン、83〜93行: 不在確認アイコン、289〜337行: 投稿マーカー、340〜346行: 調査依頼マーカー）
- 案 A 採用時: `src/locales/{ja,en,ko,zh}/translation.json`（マーカー aria-label 用キー追加）
- 代替経路の参照: `PhotoGallery`（`src/app/(home)/HomeInteractive.tsx` 経由）
- 関連テスト: 地図系 E2E（Playwright）/ axe

## 優先度
- **緊急度**: 中 / **重要度**: 中 / **理由**: WCAG レベル A に該当するが、PhotoGallery という機能的な代替経路が既に存在するため、キーボード利用者がデータへ到達する手段は確保されている。一方で数百件の無名タブストップはフォーカス操作の実用性を大きく損なうため、A/B いずれかの対応で早期に解消する価値が高い。実装は局所的だが divIcon のキャッシュ設計に触れるため中程度の注意を要する。
