## 受け入れ基準

| ID | 受け入れ基準 |
|---|---|
| AC-089-01 | `/request/[id]` に直接コメントできるスレッドが表示される |
| AC-089-02 | 自分のコメントは削除（ソフトデリート）でき、他人のコメントは削除不可 |
| AC-089-03 | closed な依頼にはコメントできない（トーストで通知）|
| AC-089-04 | 1 ユーザー 24h 30 件超で拒否される |
| AC-089-05 | コメント INSERT で依頼者と参加者に通知が届く（REQ-088 基盤） |
| AC-089-06 | 統合タイムラインで依頼コメントと結果投稿コメントが時系列で表示される |
| AC-089-07 | XSS / spam-check が既存 posts コメントと同水準で機能する |
| AC-089-08 | 未ログイン時は閲覧のみ、投稿時はサインイン誘導 |
| AC-089-09 | 既存 posts コメント / RLS テストが引き続き通る |

## リスク・トレードオフ

| リスク | 緩和策 |
|---|---|
| 既存 `comments` との二重管理 | view `survey_request_timeline` で統合表示し、UI 上の認知差は最小化 |
| polymorphic 化を見送ったことで将来コメント機能が分散 | コメント機能の統一は別大規模リファクタとして将来要件で再検討 |
| ソフトデリートで容量が増加 | 90 日経過した deleted_at 付きレコードを定期削除する scheduled function を将来追加 |
| spam-check の二重実装 | 共通関数 `check_comment_rate_limit` を抽出して両テーブルで共有 |
| 通知（REQ-088）との同時実装が前提 | REQ-088 のフックポイントを先に整備し、本 Phase で event_type を追加 |
| 統合タイムラインの並び順での認知混乱 | 各エントリに「依頼へ / 結果投稿 #X へ」のラベルを必ず付ける |
