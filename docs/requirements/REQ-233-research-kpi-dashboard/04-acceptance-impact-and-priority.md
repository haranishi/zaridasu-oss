## 影響範囲

**本 REQ が担う範囲（卒研 KPI の定義とダッシュボード化）:**
- `supabase/schema.sql` ＋ `supabase/migrations/`（新規連番）: コホート継続率 RPC・承認ファネル/量×質カウンター集計 RPC（admin 限定・`SECURITY DEFINER SET search_path=public`、必要なインデックス）。
- `src/app/admin/kpi/page.tsx`（新規ルート）・`src/views/admin/AdminKpiPage.tsx`（新規画面）・`src/views/admin/AdminLayout.tsx`（`NAV_ITEMS` 追加）。
- 集計取得フック（新規、`useAdminStats.ts` の `Promise.allSettled` パターン踏襲）。
- `src/views/PrivacyPage.tsx`（外部送信規律の通知・公表が不足する場合のみ追記）。
- GA4 プロパティ設定（データ保持 14ヶ月）= IaC 化不可のため runbook/チェックリストで管理。
- KPI Register・週次レビュー型の runbook（または本 REQ への記録）。

**本 REQ が担わない範囲（既存/兄弟 REQ との境界＝重複回避）:**
- **REQ-175（実験計測基盤・A/B・DID）**: 実験群×期間の DID 集計（`get_experiment_metrics`）と `/admin/experiments` は REQ-175 が主管。本 REQ は**全体 KPI 体系**を担い、実験別 DID 画面は残して相互リンクするのみ（介入評価ロジックは変更しない）。
- **REQ-232（GA4 行動イベント設計＝本 REQ の前提データ源）**: 投稿開始/完了等の GA4 イベント名・パラメータ・GTM 実装・PII リダクションの具体実装は REQ-232 が主管。本 REQ は「**どのファネル/コホートを GA4 探索で・どれを Supabase で見るか**」の定義と、データ保持 14ヶ月・外部送信規律の運用を担う。
- **REQ-107（計測ツール統一＝GA4 へ一本化）**: 計測系統の重複排除（Vercel Analytics 撤去）は REQ-107 が主管。本 REQ は GA4 を前提に KPI を載せるだけで、計測経路の取捨選択はしない。
- バックアップ/PII 列保護等のセキュリティは既存 REQ（REQ-179/REQ-221 等）が主管。本 REQ は集計値のみを扱い PII 列を露出しない（前提として依存）。

**他機能への影響リスク:**
- 新規集計 RPC は読み取り専用・admin 限定で、投稿/モデレーションの本番フローには影響しない。ただし `posts` 全期間スキャンの重さに注意し期間引数で絞る（NFR-233-05）。
- GA4 データ保持変更・プライバシーページ追記は機能挙動を変えないが、外部送信規律の説明不足は法令観点のリスクのため点検を AC に含める。

## 優先度

- **緊急度**: Medium / **重要度**: High
- **理由**: 通常の機能は動くが、本 REQ が無いと**卒論の中心的主張（継続率・参加率・データ品質）を、生存者バイアスを排した形で定量的に示せない**。とくに「全体平均で継続を語る」誤りと「量だけ追って品質が落ちる（Goodhart）」誤りは、卒研の論証を根本から弱める。コホート継続率と量×質カウンター指標は、データ源（`posts.user_id`/`created_at`/`status`/`accuracy`、`ai_call_logs`）が既に揃っており**低コストで実装でき効果が大きい**。GA4 データ保持 14ヶ月は「設定漏れ事故が多く、後から遡及できなくなる」非可逆リスクのため早期に締めるべき。一方、本格 BI（BigQuery/Looker）や高度な統計推論は卒研 PF として過剰であり範囲外とし、本 REQ は「KPI 定義＋ Supabase 集計＋ 1 ダッシュボード＋ GA4 探索の正しい前提」を確実に成立させることに主眼を置く。
