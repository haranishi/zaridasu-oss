## 目的

- 卒論の主張（**継続率・参加率・データ品質**）に直結する KPI を、**North Star Metric（1 つ）＋ガードレール指標＋KGI** の 3 点セットとして定義し、台帳（KPI Register）として明文化する。
- **獲得月コホート別の継続率カーブ**と**参加ファネルの段別歩留まり**を Supabase 集計 RPC で算出可能にし、全体平均の生存者バイアスを排する。
- **量×質を必ずペアにしたカウンター指標**（1 提出あたりコスト・完全率/正確率）を常設し、Goodhart 対策のガードレールとする。
- これらを **管理画面の 1 つの研究 KPI ダッシュボード**に集約し、前週比（WoW）・緑黄赤バンド・コホート表を備えて**週次 3 行レビュー**が回せるようにする。
- **GA4 のデータ保持を 14ヶ月へ変更**し、探索（ファネル/コホート/経路）の遡及を可能にするとともに、**PII 非送出**と**外部送信規律（通知・公表）**を点検・記録する。
- 既存の REQ-175（実験 DID）・REQ-232（イベント設計）・REQ-107（計測統一）と**非重複**で接続する（→「影響範囲」で境界明記）。

## 要件

### 機能要件

- [ ] FR-233-01: **KPI 体系（NSM＋ガードレール＋KGI）を定義し台帳化する。** KPI ノートの 3 点セットに従い、ザリダスの研究 KPI を確定して本 REQ もしくは runbook に **KPI Register（KPI名/目的=どの主張に繋がるか/計算式/データ源/種別=先行・遅行/目標・緑黄赤バンド/頻度/オーナー）** として記録する。少なくとも以下を含む（数値の目標は仮置きで可、3ヶ月運用後に見直す旨を明記）：
  - **North Star Metric（先行・価値・1つ固定）**: 例「週内に 2 回以上投稿した**アクティブ投稿者数（WAU 相当）**」または「**承認された有効観測レコード数**」のいずれかに確定（「価値を受け取った量」で定義し、累計DL等の虚栄指標にしない）。**NSM は 2 つ持たない**。
  - **ガードレール指標（counter-metric）**: 「完全率/正確率（後述）」「モデレーション却下率（`status='rejected'` 比）」「1 提出あたり AI コスト」など、NSM を追って壊れる副作用の歯止め。
  - **KGI（遅行・成果）**: 卒研の最終成果（例「累積有効観測レコード数」「継続投稿者の総数」）。
- [ ] FR-233-02: **獲得月コホート別の継続率を返す集計 RPC を新設する。** `posts` の `user_id`/`created_at` から「**初投稿月（獲得コホート）× 経過月（M0, M1, M2, …）の保持率（その経過月に再投稿したユーザー数 ÷ コホート人数）**」のマトリクスを返す `SECURITY DEFINER`（admin 限定・`SET search_path = public`）な RPC（例 `get_retention_cohorts(p_months int)`）を追加する。`get_experiment_metrics`（`schema.sql:1378`）の admin 判定（`request.jwt.claims` の `app_metadata.role = 'admin'` 検査、`schema.sql:1392-1397`）と同じ認可パターンを踏襲し、**全体平均ではなくコホート別カーブ**を返す。schema.sql と新規連番 migration（直近 `supabase/migrations/20260603000006_seed_experiments.sql` の後）を同期させる（REQ-003 方針）。
- [ ] FR-233-03: **参加ファネルの段別歩留まりを定義する。** 「閲覧（GA4）→投稿開始（GA4 イベント）→投稿完了（GA4 イベント or `posts` 行）→承認（`status='approved'`）」のファネルについて、(a) **GA4 探索（ファネルデータ探索）で見る段**（閲覧→投稿開始→完了。イベント定義は REQ-232 に依存）と、(b) **Supabase で見る段**（完了→承認の歩留まり＝`status` 別件数比）を切り分けて定義する。Supabase 側は admin 集計 RPC（FR-233-02 の RPC に同梱可、または `get_admin_post_stats` の拡張）で `status` 別件数・承認率を返す。**どこが漏れているか 1 段を特定**できる粒度にする。
- [ ] FR-233-04: **量×質のカウンター指標（ペア）を算出する。** 以下を結合指標として算出する集計を追加する（admin 限定 RPC）：
  - **完全率**: 必須/推奨項目（写真添付＝`photos` 非空、位置精度＝`accuracy` 非 NULL、種別/情報種別）が揃った投稿の割合。
  - **正確率（精度内率）**: `accuracy` が REQ-172 の閾値（例 30m）以内の投稿の割合（`accuracy IS NOT NULL` を分母にした内訳と、全投稿を分母にした内訳の両方を明示）。
  - **1 提出あたり AI コスト**: AI 判定コスト（`ai_call_logs` 由来＝`get_ai_cost_summary` のトークン集計に `AdminAiCostPage.tsx:10-20` の概算単価を適用）÷ 承認投稿数。
  各指標は**必ず対になる「量」（投稿数・承認数）と並べて表示**し、Goodhart（量だけ追って質が死ぬ）を検知できるようにする。
- [ ] FR-233-05: **研究 KPI ダッシュボード画面を新設する。** 管理画面に新ルート（例 `/admin/kpi`、`src/app/admin/kpi/page.tsx` ＋ `src/views/admin/AdminKpiPage.tsx`）を追加し、`AdminLayout.tsx:121-130` の `NAV_ITEMS` に項目（例「📈KPI」）を追加する。画面は KPI ノートの設計に従い、最低限：
  - **NSM＋ガードレール＋KGI のサマリーカード**（現在値・**前週比（WoW）**・**緑黄赤バンド**の色分け）。
  - **コホート継続率の三角マトリクス表**（FR-233-02）。
  - **量×質ペアのカウンター指標**（FR-233-04、量と質を横並び）。
  - **承認ファネルの段別歩留まり**（FR-233-03 の Supabase 側）。
  - 各 KPI に「データ源」「定義」を併記（虚栄指標化・定義揺れの防止）。
  既存の `/admin/ai-cost`・`/admin/experiments` とは**重複させず相互リンク**する（実験別 DID は REQ-175 の画面に残す）。
- [ ] FR-233-06: **GA4 データ保持を 14ヶ月へ変更し記録する。** GA4 管理 →「データの収集と修正 → データ保持」を**初期値 2ヶ月→14ヶ月**に変更し、変更済みであることを runbook/チェックリストに記録する（IaC 化不可のため）。あわせて GA4 探索で見る KPI（ファネル/コホート/経路）が**14ヶ月遡及できる**ことを前提として明文化する。標準レポートには影響しない旨も注記。
- [ ] FR-233-07: **PII 非送出と外部送信規律（通知・公表）を点検・是正する。** (a) GA4 へ **PII（メール/氏名/電話）やそれらを含む URL クエリを送らない**こと（フォーム値・`?q=` 等のリダクションを GTM/イベント設計側で担保＝具体実装は REQ-232 と連携）、(b) **改正電気通信事業法の外部送信規律**に基づく**通知・公表**（プライバシーポリシー/外部送信の説明）が `src/views/PrivacyPage.tsx` に十分含まれるかを点検し、不足あれば追記する。EU/UK 向けトラフィックを想定する場合のみ同意バナー＋Consent Mode v2 を別途検討する旨を注記（現状は国内前提）。
- [ ] FR-233-08: **週次レビューの型を運用に組み込む。** KPI ノートの「数字→なぜ→打ち手」を**毎週 3 行**で残すレビュー手順（cadence 固定・WoW・緑黄赤・打ち手は 1 つだけ）を runbook 化し、ダッシュボード画面からその手順へ導線（リンク/注記）を置く。卒論の考察に使えるよう、レビュー記録の保存先（Obsidian 等）を明記する。

### 非機能要件（該当する場合のみ）

- [ ] NFR-233-01: **集計は DB 側で行い全行転送しない。** FR-233-02〜04 の集計は Supabase 集計 RPC（`GROUP BY`/`count(DISTINCT)`/`percentile_cont` 等）に寄せ、`get_admin_post_stats`（`schema.sql:913-965`）/`get_experiment_metrics`（`schema.sql:1378-1441`）と同様にクライアントへ生行を流さないこと。コホート/ファネル算出に必要なインデックス（`idx_posts_status*`＝`schema.sql:532-533`、`created_at`、`user_id`）の有無を確認し、不足あれば追加する。
- [ ] NFR-233-02: **認可とプライバシー。** 新規 RPC は admin 限定（`get_experiment_metrics` と同じ JWT claims 検査）かつ `SECURITY DEFINER SET search_path = public` で、`reporter_ip` 等の PII 列（REQ-179）を返さないこと。KPI ダッシュボードは個票ではなく**集計値のみ**を表示し、しきい値以下の小セルで個人が再識別されないよう留意する（GA4 側のデータ秘匿しきい値とも整合）。
- [ ] NFR-233-03: **schema/型同期・回帰ゼロ。** `npm run schema:check`（schema/型同期）と CI（rls-tests/E2E）が green であること。新規 RPC は migration と schema.sql でドリフトを作らない（過去 migration は改変せず新規連番で追補）。
- [ ] NFR-233-04: **再現性のある定義。** KPI の計算式・コホート定義・閾値（精度 30m 等）は KPI Register と RPC コメントの両方に記述し、卒論・第三者が同じ手順で再計算できること。指標は「量×質ペア」を崩さないことをレビュー観点に追加する。
- [ ] NFR-233-05: **パフォーマンス。** コホート/ファネル RPC は管理者がたまに開く想定だが、`posts` の全期間スキャンが重くなりすぎないよう期間引数（`p_months` 等）で範囲を絞れること。ダッシュボード初期表示で過大なクエリを並列発火しないこと（`useAdminStats.ts:89-105` の `Promise.allSettled` 部分失敗許容パターンを踏襲）。
