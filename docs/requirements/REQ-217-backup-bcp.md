# REQ-217: バックアップ・BCP（事業継続）の整備

## 背景

ザリダスは卒業研究の市民科学 PF（Next.js 15 / Supabase: Postgres + RLS + Auth + Storage / Vercel）で、収集データ（投稿・写真・音声・調査依頼・コメント等）がそのまま研究成果である。すなわち **データ消失 = 研究成果の喪失**であり、誤操作・ランサムウェア・プロバイダ障害・アカウント停止などからの復旧能力（バックアップと復元）は、機能要件と同等以上の優先度を持つ運用要件である。

本 REQ は Obsidian ノート **32_Backup_BCP**（バックアップ戦略・3-2-1-1-0・RPO/RTO・リストア訓練）と **11_Database_Hardening**（DB 防御の一環としての論理バックアップ）を下敷きとし、リポジトリの現状（バックアップ自動化・復元手順が一切存在しないこと）を起点に、一人運用の卒研 PF として現実的な最小構成から段階的に整備する。

本 REQ は「バックアップと復元」に集中する。隣接する REQ-218（クラウド課金ガードレール = ストレージ肥大やコスト暴走の監視）・REQ-220（インシデント / 漏洩対応 runbook）とは目的を分け、本書では復旧能力の確立のみを扱う。

> 前提（プラン）について: 本 REQ 執筆時点で Supabase の契約プラン（無料 / Pro）はリポジトリから確認できない（`supabase/config.toml` はローカル開発設定のみで、バックアップ / PITR はダッシュボード側設定のため痕跡が無い）(推測)。そこで本書は **無料枠・Pro いずれでも成立する段階提案**とし、Pro 固有機能（日次自動バックアップ・PITR）は「Pro 移行時に有効化する」要件として分離する。現プランは実装着手時に運用者が確認し、本書の該当箇所に追記すること。

## 現状の問題

（ファイルパス:行番号、または「設定が存在しない」事実）

### (1) DB の定期バックアップ自動化がリポジトリに一切存在しない
- ワークフローは `.github/workflows/ci.yml` の 1 本のみで、cron トリガー（`schedule:`）も `pg_dump` / `supabase db dump` を実行するジョブも**存在しない**（`grep -n "schedule:\|pg_dump\|supabase db dump\|backup" .github/workflows/ci.yml` が 0 件、`.github/workflows/` 配下は `ci.yml` のみ）。
- `package.json` の `scripts`（`package.json` 全 18 スクリプト）にも `db dump` / `pg_dump` / `backup` 系は**無い**。手動バックアップ手段すらコード化されていない。
- 無料枠の Supabase は自動バックアップが提供されない（または保持が極端に短い）ため(推測)、現状は **DB のバックアップが 0 件**であり、誤 `DELETE` / `UPDATE`、テーブル DROP、プロジェクト消失時に復旧手段が無い。
- CI には既に `SUPABASE_ACCESS_TOKEN` / `SUPABASE_PROJECT_REF` の Secrets が設定済み（`.github/workflows/ci.yml:117-118`、`rls-tests` ジョブで使用）で、`supabase` CLI も CI で利用されている。すなわち**バックアップ自動化に必要な土台は既にあるのに、それを使うジョブが無い**状態。

### (2) Storage の実体ファイル（画像 / 音声）はそもそも DB バックアップに含まれない
- ザリダスは公開バケットを 2 つ持つ:
  - `post-photos`（公開・5MB・jpeg/png/webp/heic、`supabase/schema.sql:409-417`、`supabase/migrations/20240101000000_initial_schema.sql:555-556`）
  - `post-audio`（公開・1MB・webm/mp4/mpeg/ogg、`supabase/schema.sql:1270-1278`）
- 投稿写真・音声は Storage に保存され、URL のみが `posts` 行に残る（アップロード: `src/hooks/usePostForm.ts:138-180`、`src/lib/uploadAudio.ts:28`、`src/hooks/useOfflineQueue.ts:62-65`。バケット定数 `post-photos` は `src/utils/storage.ts:10-18` ほか多数）。
- **`pg_dump` / `supabase db dump` は Storage オブジェクトの実体（バイナリ）を含まない**。DB だけバックアップしても写真・音声は復元できず、`posts` 行のリンクは切れる。Storage を別途バックアップする仕組みは**存在しない**（`grep` で `post-photos` のエクスポート / download を行う運用スクリプトは検出されず、参照箇所はすべてアプリ実行時の upload/remove/getPublicUrl）。

### (3) 復元手順書・リストア訓練・RPO/RTO がどこにも無い
- `docs/runbooks/` には `ai-model-rollback.md` / `edge-function-deploy.md` / `gemini-key-rotation.md` 等の運用手順はあるが、**バックアップ / 復元 / DR の runbook は無い**（`docs/runbooks/` 一覧に該当なし、`grep -rln "リストア\|復元\|RPO\|RTO\|PITR" docs/` のヒットは過去 REQ の付随言及のみで手順書ではない）。
- 「いつのバックアップから・どの順序で・どこへ復元するか」が未定義で、目標復旧時点（RPO）・目標復旧時間（RTO）も設定されていない。バックアップを取っていても**復元できる保証が無い**（取りっぱなしで検証 0 回）。

### (4) 3-2-1（できれば -1-0）の観点で見ると現状はコピー 1（本番のみ）
- 現状は本番 DB / Storage の 1 コピーのみ。媒体・拠点の冗長化、オフライン / イミュータブル世代、復元テストのいずれも無い。ランサムウェアやアカウント乗っ取りで本番が暗号化 / 削除されると同時に全滅する。

## 目的

- DB と Storage の双方について、**定期・自動・暗号化・オフサイト**のバックアップを確立し、誤操作・ランサムウェア・プロバイダ障害から復旧可能にする。
- **復元手順を文書化し、最低 1 回のリストア訓練で「復元できる」ことを実証**する（取りっぱなしにしない）。
- 一人運用の卒研 PF として無理のない **RPO / RTO 目標**を定め、3-2-1（将来的に -1-0）に近づける。
- Pro 移行時の **PITR 有効化**を移行チェックリストとして用意し、論理バックアップと役割分担させる。

## 要件

### 機能要件

- [ ] FR-217-01: **DB 論理バックアップの自動取得（最小構成）。** GitHub Actions に cron スケジュール（例: 毎日 1 回）のジョブを追加し、`supabase db dump`（または `pg_dump`、本番 DB 接続文字列を Secrets 経由で使用）で本番 DB のロジカルダンプを取得する。`.github/workflows/ci.yml:117-118` で既存の `SUPABASE_ACCESS_TOKEN` / `SUPABASE_PROJECT_REF` を流用しつつ、ダンプに必要な DB パスワード / 接続文字列は新規 Secret（例 `SUPABASE_DB_URL`、本番 ref は `edxmkqmjzbarjdgnkcvc`、`docs/runbooks/edge-function-deploy.md:20` 参照）として追加する。ワークフローは `ci.yml` とは別ファイル（例 `.github/workflows/backup.yml`）に分けることを推奨。
- [ ] FR-217-02: **バックアップの暗号化とオフサイト保管。** 取得したダンプを**保存前に暗号化**（例: `age` または `gpg` で公開鍵暗号、秘密鍵は Actions に置かず運用者ローカルでのみ復号）し、本番（Supabase / Vercel）とは別の場所に保管する。保管先は以下のいずれかから選定し本書に記録する: (a) GitHub Actions の `actions/upload-artifact`（保持期間設定つき、短期向け）、(b) 別プロバイダのオブジェクトストレージ（例 Cloudflare R2 / Backblaze B2 / 別アカウントの S3 等、長期 + オフサイト）。**平文ダンプをアーティファクト / リポジトリに残さない**こと。
- [ ] FR-217-03: **Storage バケットの定期エクスポート。** `post-photos` / `post-audio` の実体ファイルを定期的に取得し、DB ダンプと同じ世代管理下に保存する。手段は (a) `supabase storage` CLI / S3 互換プロトコル（`config.toml:40-41` で s3_protocol 有効）でのミラー、(b) サービスロールキーを用いた一覧 + ダウンロードスクリプトのいずれか。**「DB だけでは写真 / 音声は戻らない」**前提を解消することが目的。頻度は DB と同等かやや低くてよい（差分が大きいため、初期はフルコピー + 後日 rsync 的差分を検討）。
- [ ] FR-217-04: **世代保持と 3-2-1 への接近。** バックアップは複数世代を保持し（例: 日次を 7〜14 世代 + 週次を 4〜8 世代のローテーション）、最低でも「本番 + バックアップ保管先」の 2 拠点、可能なら**もう 1 系統をオフライン / イミュータブル**（例: 月 1 回手元 HDD へ退避、またはオブジェクトロック付きバケット）に置く。3-2-1（3 コピー・2 媒体・1 オフサイト）を満たし、将来的に -1-0（1 オフライン / イミュータブル・復元テスト 0 エラー）を目指す。古い世代の自動削除（保持期間超過分のパージ）も含める。
- [ ] FR-217-05: **復元手順書（runbook）の作成。** `docs/runbooks/` に DB + Storage の復元手順書（例 `backup-restore.md`）を新規作成する。最低限、(a) バックアップの所在と暗号鍵の管理、(b) 暗号化ダンプの復号、(c) 新規 / 既存 Supabase プロジェクトへの DB リストア手順、(d) Storage バケットの再作成 + ファイル投入手順、(e) 復元後の整合チェック（`posts` 行の写真 / 音声 URL がバケット上の実体と一致するか）、(f) RLS / トリガー / バケットポリシーが migration 適用で再構築される旨を、既存 runbook（`docs/runbooks/edge-function-deploy.md` の書式）に倣って記述する。
- [ ] FR-217-06: **リストア訓練の実施と記録。** 上記手順書に沿って**最低 1 回**、検証用 Supabase プロジェクト（または `supabase start` のローカル環境）へ実際に復元し、アプリが起動 + データ表示 + 画像 / 音声参照まで通ることを確認する。実施日・所要時間・つまずき・手順書の修正点を runbook に追記する（訓練結果のフィードバックループ）。
- [ ] FR-217-07: **誤操作・ランサムウェア耐性の明文化。** 復元手順書に「誤 `UPDATE` / `DELETE` / テーブル DROP からの復旧（直近正常世代の選択）」と「本番が暗号化 / 削除された場合の復旧（オフライン / イミュータブル世代からの再構築）」のシナリオを記載する。イミュータブル世代があることで、本番への書き込み権限を奪われてもバックアップまで遡及破壊されない設計であることを示す。
- [ ] FR-217-08: **Pro 移行時の PITR 有効化（将来要件）。** Supabase Pro へ移行する場合のチェックリストを runbook に用意する: (a) ダッシュボードで日次自動バックアップ + Point-in-Time Recovery アドオンを有効化、(b) PITR の保持期間設定、(c) PITR は Supabase 内（同一プロバイダ）に閉じるため、**オフサイト / オフラインの論理バックアップ（FR-217-01〜04）は PITR 後も継続**する旨（プロバイダ障害・アカウント停止に PITR は無力）。

### 非機能要件

- [ ] NFR-217-01: **秘密値の非露出。** DB 接続文字列・サービスロールキー・暗号鍵は Secrets / 環境変数のみで扱い、リポジトリ・ログ・アーティファクトに平文で残さない。バックアップ自体も暗号化済み（FR-217-02）であること。本書および runbook に実際の秘密値を書かない。
- [ ] NFR-217-02: **RPO 目標。** 目標復旧時点を定義する。最小構成（日次バックアップ）では **RPO = 24 時間以内**（最大で直近 1 日分の損失）を初期目標とし、Pro + PITR 移行後は **RPO = 数分〜1 時間**を目標とする。卒研の重要マイルストーン直前は手動バックアップで RPO を縮める運用も明記する。
- [ ] NFR-217-03: **RTO 目標。** 目標復旧時間を定義する。一人運用前提で **RTO = 数時間〜1 営業日以内**（手順書に沿って新規プロジェクトへ復元しアプリ再接続が完了するまで）を初期目標とし、リストア訓練（FR-217-06）の実測値で見直す。
- [ ] NFR-217-04: **コスト現実性（REQ-218 と整合）。** バックアップ保管 / 転送コストが卒研 PF として過大にならない構成にする（無料枠 / 低額枠で完結、世代保持で容量を制御）。詳細なコスト監視 / ガードレールは REQ-218 に委ねる。
- [ ] NFR-217-05: **バックアップジョブの可観測性。** 自動バックアップの成功 / 失敗が運用者に届くこと（Actions の失敗通知 / 既存の通知経路の活用）。**「気づかないうちに数週間バックアップが落ちていた」を防ぐ**こと。

## 受入条件

- [ ] AC-01: `.github/workflows/` に cron スケジュールの DB バックアップジョブが存在し（`schedule:` を含む）、手動実行（`workflow_dispatch`）でも成功して暗号化ダンプが保管先に作られる。平文ダンプがアーティファクト / リポジトリに残っていない。
- [ ] AC-02: `post-photos` / `post-audio` の実体ファイルが定期的にバックアップ保管先に取得されており、保管物だけで「DB + 写真 + 音声」が揃う（DB ダンプ単体では揃わないことの裏返しが解消されている）。
- [ ] AC-03: バックアップが複数世代保持され、保持期間超過分が自動削除される。最低 2 拠点（本番 + オフサイト）に存在し、可能ならオフライン / イミュータブル世代が 1 つ以上ある（3-2-1 達成、-1-0 への進捗が記録されている）。
- [ ] AC-04: `docs/runbooks/` に DB + Storage の復元手順書が存在し、暗号化ダンプの復号からアプリ再接続・整合チェックまでが記載されている。
- [ ] AC-05: リストア訓練を**最低 1 回**実施し、検証 / ローカル環境で復元したアプリがデータ表示 + 画像 / 音声参照まで通ることを確認した記録（実施日・所要時間・修正点）が runbook にある。RTO 実測値が NFR-217-03 と照合されている。
- [ ] AC-06: RPO / RTO 目標が runbook に明記され、Pro 移行時の PITR 有効化チェックリスト（PITR 後も論理オフサイトバックアップを継続する旨を含む）が用意されている。
- [ ] AC-07: バックアップジョブの失敗が運用者に通知される経路が確認できる（意図的に失敗させると通知 / 失敗ステータスが届く）。

## 影響範囲

- `.github/workflows/`（新規 `backup.yml` 等。DB ダンプ + Storage エクスポート + 暗号化 + 保管 + 世代パージの cron ジョブ）
- GitHub Secrets（DB 接続文字列 / サービスロールキー / 暗号公開鍵などの追加。値は書かない）
- `docs/runbooks/`（新規 `backup-restore.md`: 復元手順 + リストア訓練記録 + RPO/RTO + PITR チェックリスト）
- `package.json`（任意: 手動バックアップ / 復元補助スクリプトを追加する場合のみ）
- 外部保管先（任意で R2 / B2 / 別 S3 等のオフサイトストレージ、オフライン世代用の手元媒体）
- アプリ本体のコードには影響なし（運用 / CI / ドキュメントのみ）。Supabase ダッシュボード設定（Pro 移行時の PITR）は別途運用者作業。

## 優先度

- **緊急度**: High / **重要度**: Critical
- **理由**: ザリダスは卒業研究 PF であり、収集データの消失は研究成果そのものの喪失に直結する。にもかかわらず**現状は DB / Storage ともバックアップが 0 件**（自動化・手動手段・復元手順のいずれも存在しない）で、誤 `DELETE`・ランサムウェア・プロバイダ障害・アカウント停止のいずれが起きても復旧不能という、運用上もっとも重いリスクを抱えている。CI には既に Supabase Secrets と CLI 利用の土台があるため、最小構成（日次ダンプの暗号化オフサイト保管 + Storage エクスポート + 復元手順 + リストア訓練）は低コストで着手でき、費用対効果が極めて高い。Pro 移行時の PITR はその上に重ねる将来要件として分離する。
