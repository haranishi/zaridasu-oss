## 影響範囲

**本 REQ が担う範囲（ブランド資産そのもの）:**
- `public/icon-192.svg`・`public/icon-512.svg`（絵文字→マスコットパスへ作り直し）
- `public/favicon.ico`（新規作成。または Next.js `app/` 規約アイコン）
- `public/og-image.svg`・`public/og-image.png`（新マスコット/ロゴ・新コピー・新構図へ差し替え）
- `public/opensearch.xml`（ホストを `zaridasu.com` に統一・実在 favicon を参照）
- `public/mascot.svg` 等（新規。マスコット原型・空状態用ポーズ／命名は実装時確定）
- `src/app/layout.tsx`（`icons` に `favicon.ico` 追加。`theme-color` は HEX 整合の確認のみ）
- `src/app/manifest.ts`（アイコン配列を新シンボルへ）
- `docs/brand/brand-memo.md` 等（**新規**: 1 枚ブランドメモ＝マスコット仕様・Voice&Tone・HEX・書体・ロゴ Do/Don't・OG 構図ガイドライン）
- ヘッダのロゴ表現（`src/views/LandingPage.tsx:220` 周辺・`src/components/layout/Header.tsx`）への組み合わせ型ロゴ適用は、本 REQ では**ガイドライン提供＋低リスクな差し替え**に留め、UI 全体への展開は段階的に行う

**本 REQ が担わない範囲（既存・関連 REQ との境界＝重複回避）:**
- **OG 画像の動的生成ロジック**（`src/app/api/og/route.tsx`）は REQ-027（動的メタデータ/OGP）と REQ-042（入力サニタイズ）が主管。本 REQ は「OG に載せるブランド表現・被写体構図のガイドライン」を渡すのみ。
- **どのページにどの OG/Twitter タグを出すか**は REQ-027（ページ別）・REQ-181（LP）が主管。
- **デザイントークン（CSS 変数化）・色覚多様性/コントラスト a11y の実装**は REQ-224 が主管。本 REQ は公式 HEX の確定と 1 枚メモへの記載まで。
- **空状態（Empty）/ローディング/エラーの 3 状態 UI 実装**は REQ-222 が主管。本 REQ はマスコット挿絵（素材）を提供／方針を渡す。

**他機能への影響リスク:**
- favicon/アイコン/OG の差し替えは静的アセット中心で機能ロジックへの影響は小さいが、(a) `manifest.ts`/`layout.tsx` のアイコンパスを変えると PWA インストール・タブアイコンに影響するため `npm run build` 後に `/manifest.webmanifest` と各メタ出力を確認する。(b) `og-image.png` の差し替えは SNS シェアカードに即反映されるため、差し替え後に OGP デバッガで表示確認する。(c) Web フォント追加（FR-225-07）を行う場合のみ初期表示パフォーマンスに影響しうるため `display: swap`/サブセットで緩和し REQ-224 と整合させる。

## 優先度

- **緊急度**: Medium / **重要度**: High
- **理由**: 機能は動いており即時の不具合ではない（緊急度 Medium）。一方、ザリダスは広告・SNS・チラシ（QR）流入の受け皿として LP を持ち（REQ-176）、第一印象＝シェアカード・タブアイコン・ホーム画面アイコンの一貫性が**認知と信頼に直結**する（ブランド VI ノート §6）。現状は「OS 標準の、しかも種が違う絵文字」「壊れた `favicon.ico` 参照」「旧ドメイン参照」という、ブランドとして致命的に弱い土台のままで、REQ-027/REQ-181 で整えた OG の器に**載せる中身（固有の図像・声）が無い**。マスコットと 1 枚ブランドメモを一度作れば、以降の OG（REQ-027）・トークン（REQ-224）・空状態（REQ-222）・SNS シェア（後続 REQ）すべてが同じ正本を参照できるため、卒研 PF として早期に確定する価値が高い（重要度 High）。一方、UI 全体へのロゴ展開や動的 OG への組み込みは後続に分割してよく、本 REQ は「マスコット・ロゴ・favicon 体系・1 枚ブランドメモ・OG 構図ガイドライン」を確実に作り切ることを主眼とする。
