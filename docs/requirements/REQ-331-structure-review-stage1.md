## これは何か

本人の悩み（2026-10-01）は「機能を作ったり直したりするとき、入れにくい。バラバラな気がする」。develop `42a6a99` を読み取りだけで調べた結果、層の向き（app → views → components → hooks → lib）はほぼ守られていた。逆向きの import は3本で、どれも型か小さな部品の参照だった。全面的な作り直しは要らない。

重さの正体は3つあった。

1. **同じ事実を手で何か所にも書いている。** DB の形は migration・`schema.sql`・`database.types.ts` の3か所に手書きで、REQ-329・325・253 の schema.sql への追加は、コメントを除くと migration の写しだった（127行中126、24行中24、86行中86）。それでも schema.sql には、アプリが使う3表と3関数が入っていない。投稿の INSERT も2か所あり、電波が戻ってからの再送の側には今も2列が欠けている。
2. **DB を触るコードが層をまたいで散っている。** DB 呼び出し117か所のうち、データ層 `src/lib/data/` にあるのは26か所（22%）。ESLint が止めているのは `.from('表')` だけで、RPC の33か所は対象外だ。
3. **機能の差し込み口が巨大ファイルしかない。** REQ-329 は src の13ディレクトリに散り、大きいファイル上位20のうち6本を編集した。52ファイルを仕分けると、機能そのものに要る変更が36、構造が原因の変更が14だった。

件数より危ないのは、構造が原因の変更のうち少なくとも4か所が「書き忘れても型検査も ESLint も通る」ことだ。

## 段1で決めたこと

- **投稿の INSERT**: 行の組み立てを `src/lib/data/posts-write.ts` の1関数にし、通常の送信・再送・REQ-330 の不在記録から呼ぶ。再送でも `image_hashes` と `experiment_assignments` を送る。REQ-185 の目標が「同じ列の集合で復元」で、欠けている理由がコードにも文書にも見当たらないためだ。完了の判定は「posts への `.insert(` が lib/data の外に0か所」と「通常と再送で送るキーが一致する単体テスト」。
- **機能フォルダ**: 自分の表を持ち、入口が地図のレイヤー・シート・管理画面のどれかで、ほかの機能からは決めた1〜2ファイルでしか使われない機能だけを置く。posts・地図本体・認証のような中核は動かさない。index.ts でまとめて再 export する形（バレル）は作らない。1関数を使うだけで機能全体がホームの JS に載りうるからだ。ESLint のデータ層の許可に `src/features/*/data/**` を足す。
- **右下ボタン**: MapView に入れ物を1つ置き、各レイヤーは自分のボタンをそこへ差し込む。
- **必須セット**: DB を変えるとき（migration・schema.sql・型・pg-tap・reapply・索引）、画面の文言を足すとき（4言語）、挙動を変えるとき（docs/current）に触る場所と、それぞれを検査するスクリプトを規約文書に書く。自動検査にできた項目は一覧から消す。リポジトリ直下の AGENTS.md は `next dev` が作る未追跡ファイルなので使わない。

右下ボタンは 390x844 と 1440x900 で、変更前と画素の差が0だった。見た目は変わっていない。再送の列の組が通常送信と一致することは単体テストで固定し、わざと列を消すと落ちることも確かめた。

投稿詳細 `/post/[id]` の初回 JS は 1.6 kB 増えた（予算内）。理由は、編集・削除のために読む `posts-write.ts` に INSERT の組み立てが同居したことにあり、気になれば INSERT だけを別のファイルに分ければ元の大きさに戻せる。再送の `experiment_assignments` は、再送した時点の割付になる。
