## 実装ロードマップと依存関係

```
Phase 1 (REQ-085: 一覧ページ)
    │  ※ 単体で完結。先に着手すると UX 効果が最も高い
    ▼
Phase 2 (REQ-086: 結果投稿フロー)
    │  ※ 一覧から導線を作るため Phase 1 完了が望ましい
    ▼
Phase 3 (REQ-087: 応答 / 協力)
    │  ※ Phase 2 の status 遷移ロジックと相互参照
    ▼
Phase 4 (REQ-088: 通知)
    │  ※ Phase 3 の応答イベントを通知トリガーに使うため後段
    ▼
Phase 5 (REQ-089: コメント直結化)
       ※ DB スキーマ変更を伴うため最後
```

## リスク・トレードオフ

| リスク | 影響 | 緩和策 |
|---|---|---|
| status 自動遷移によるユーザーの認識ずれ | 「自分でクローズしていないのに勝手に変わった」混乱 | `responded` は中間状態と明示し、closed のみ owner 操作に限定 |
| 通知の過剰配信で opt-out が増える | 通知機能自体が無価値化 | 市区町村粒度に絞る + 1 日 1 通までのダイジェスト化を検討 |
| 応答機能のスパム | 応答数水増しで投稿者に誤った期待 | レート制限 + 1 ユーザー 1 依頼につき 1 応答の unique 制約 |
| コメント直結化での既存データ移行 | 過去の posts 経由コメントが孤立 | Phase 5 で view を作り両者を統合表示 |
| 旧ドキュメント `requirements-sos-help-request.md` との乖離 | 仕様の二重管理 | Phase 1 完了時に旧ドキュメントを deprecated に降格 |

## サマリー

5 Phase 構成（Phase 1〜5）で、現状 55% の調査依頼機能を **依頼から結果フィードバックまで完結するループ**に仕上げる。**Phase 1（一覧ページ）が UX 改善効果として最大**であり、ここから着手することで「依頼が見つけられない」現状の最大の不満を解消する。

4. 通知（Phase 4）は Phase 3 完了後に着手し、応答イベントを通知トリガーとして再利用する
