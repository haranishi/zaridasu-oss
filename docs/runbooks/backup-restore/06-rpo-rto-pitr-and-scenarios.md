## (h) RPO / RTO 目標（NFR-217-02 / NFR-217-03）

| 指標 | 最小構成（無料枠 / 日次論理バックアップ）| Pro + PITR 移行後（→ §(i)）|
|---|---|---|
| **RPO**（許容データ損失）| **24 時間以内**（cron は毎日 1 回 = 最大直近 1 日分の損失）| **数分〜1 時間**（PITR）|
| **RTO**（復旧完了まで）| **数時間〜1 営業日以内**（新規プロジェクト作成 + スキーマ適用 + DB/Storage 投入 + 整合チェック。一人運用前提）| 同〜短縮（PITR は同一プロジェクト内巻き戻しで速い）|

- **重要マイルストーン直前**（学会・中間/最終発表・データ提出前など）は、`backup.yml` を
  `workflow_dispatch` で**手動起動して RPO を縮める**運用を併用する（NFR-217-02）。
- RTO は**リストア訓練 §(g) の実測値**で見直す（机上値のまま放置しない）。

## (i) Pro 移行時の PITR 有効化チェックリスト（FR-217-08 / AC-06）

Supabase Pro へ移行する場合に実施する。**PITR は論理オフサイトバックアップの置き換えではなく上乗せ。**

- [ ] Dashboard → Database → Backups で**日次自動バックアップ**を確認 / 有効化
- [ ] **Point-in-Time Recovery アドオン**を有効化
- [ ] PITR の**保持期間**を設定（例 7 日。卒研の運用に合わせて調整）
- [ ] 現プラン（無料 / Pro）を本 runbook §0 に追記する
- [ ] **PITR 後も FR-217-01〜04 の論理オフサイト / オフラインバックアップは継続**する
      （理由: PITR は **Supabase 内（同一プロバイダ）に閉じる**ため、**プロバイダ障害・アカウント停止・
      請求トラブルによるプロジェクト凍結には無力**。オフサイト / イミュータブル世代だけがこれらに耐える）
- [ ] PITR からの復旧手順（巻き戻し先時刻の選び方）を本 runbook に追記する

## (j) 誤操作 / ランサムウェア シナリオ別 復旧（FR-217-07）

| シナリオ | 復旧方針 |
|---|---|
| **誤 `UPDATE` / `DELETE`**（一部行）| 直近正常世代の暗号化ダンプを §(b)→§(c) で復号 → **影響テーブルのみ**抽出して流す（全体上書きは避ける）。Pro なら PITR で事象直前に巻き戻す方が速い |
| **テーブル DROP / スキーマ破壊** | §(f) でスキーマ再適用 → §(c) でデータ投入 → §(e) 整合チェック |
| **本番が暗号化 / 削除された（ランサムウェア・乗っ取り）**| 本番は信用しない。**新規プロジェクト**を作り、§(f)→(c)→(d)→(e) で再構築。鍵は CI 外のローカルにあるため攻撃者は復号できない。**オフライン / イミュータブル世代（コピー -1）から復元**すれば本番への書き込み権限を奪われても遡及破壊されない |
| **GitHub アカウント / Supabase アカウント停止**| Artifacts が使えない可能性。**オフサイト（コピー3）/ オフライン（-1）世代**から復元。だからこそ単一プロバイダに依存しない多拠点が要る |
