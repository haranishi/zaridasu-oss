## 原本の扱い（chain of custody）

「後で第三者（個人情報保護委員会・専門家・各社サポート）に説明できる」状態にしておく。

1. **原本は読み取り専用**にして触らない。調査・加工は必ず**コピー**に対して行う。
2. 各保全ファイルについて、可能なら次を記録する:
   - ファイル名 / 内容の概要
   - 取得元（例: Supabase SQL Editor / Vercel Billing 画面）
   - 取得者・取得時刻（TZ 付き）
   - 保存場所
   - **SHA-256 ハッシュ**（改ざんされていないことの証跡）
3. ハッシュの取り方（例）:
   ```bash
   shasum -a 256 audit_logs_2026-06-16.csv
   # → 出力されたハッシュ値を上記の記録表に控える
   ```
4. 保全物一式は、本人のみアクセスできる安全な場所（暗号化したフォルダ / プライベートな保管先）に置く。

### chain of custody 記録テンプレ

| ファイル | 取得元 | 取得者 | 取得時刻(JST) | SHA-256 | 保存場所 |
|---|---|---|---|---|---|
| | | | | | |

---

## やってはいけないこと

- 封じ込め（失効・削除・公開停止）を、保全より先に始めて証拠を消す。
- 原本を直接編集・上書きする（必ずコピーで作業）。
- 「ログがあるから大丈夫」と監査ログだけを信頼する（fire-and-forget で欠落し得る）。
- 保全物（秘密値・PII を含み得る）をチャット / 公開チケット / スクショ共有に貼る。
- ハッシュ・取得時刻を取らずに保全物を量産し、後で出所が説明できなくなる。
