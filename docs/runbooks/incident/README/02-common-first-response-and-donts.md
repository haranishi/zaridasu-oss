## 共通初動チェックリスト（8 ステップ）

どのインシデントでも、まずこの 8 ステップの順序で動く。各 runbook 冒頭のチェックリストはこれをケースに具体化したもの。

```
[1] 記録          いつ・何に気づいたか。発見時刻(TZ付き)・発見者・現象・関連 URL をメモ開始
[2] 証拠保全       消える前にログ・請求・監査履歴を元形式で書き出す（→ evidence-preservation.md）
[3] 封じ込め       被害の拡大を止める（失効・公開停止・kill switch・セッション破棄 等）
[4] 影響範囲特定   何が・どこまで・誰に影響したか（データ種別・件数・期間）
[5] 一次連絡       関係者へ「確認中」を共有（確約はしない）。重大なら早めに各社サポートへ
[6] 通報・相談     公的窓口・各社サポート・(個人データなら)個人情報保護委員会の要否判断
[7] 復旧          安全を確認してから本番を戻す。必要ならバックアップから復元
[8] 再発防止       事後記録（タイムライン）・恒久対策・runbook 更新
```

### ステップごとの最小アクション（共通）

- **[1] 記録**: 時刻はタイムゾーンを必ず付ける（例 `2026-06-16 14:32 JST`）。「気づいたきっかけ（アラート / 請求 / 通報 / 自分で発見）」も書く。以後すべての操作を時系列で追記していく（このメモが後の確報・報告書の素になる）。
- **[2] 証拠保全**: **封じ込めより前に**、消えうる証拠（ログ・請求明細・監査履歴・該当画面）を書き出す。詳細と保全対象一覧は [evidence-preservation.md](./evidence-preservation.md)。
- **[3] 封じ込め**: ケース別 runbook の手順に従う。「失効 → 履歴削除」「公開停止 → 原因究明」の順を守る（逆にしない）。
- **[4] 影響範囲特定**: 「最悪どこまで届いたか」を保守的に見積もる。確証がない範囲は「不明（調査中）」と明記し、安全側に倒す。
- **[5] 一次連絡**: 一人運用でも、利用者・指導教員等への一次連絡が要るケースがある。文面テンプレは [contacts.md](./contacts.md)。
- **[6] 通報・相談**: 個人データ漏洩は個人情報保護委員会への報告義務の判断が要る（→ [04-personal-data-breach.md](./04-personal-data-breach.md)）。判断に迷う＝相談する。
- **[7] 復旧**: 封じ込め前の状態にそのまま戻さない（同じ穴が残る）。データ損失が疑われるなら [05-service-outage.md](./05-service-outage.md) 経由で復元 runbook へ。
- **[8] 再発防止**: 「対応したつもり」で閉じない。各 runbook 末尾の **終了条件**を満たして初めてクローズする。

## やってはいけないこと（共通 NG）

- 先に証拠（ログ・コミット・画面・請求明細）を消す/上書きする。**記録 → 保全が先**。
- 秘密漏洩で、失効より先に Git 履歴の書き換え（force push / filter-repo）をする。**まず発行元で失効**してから履歴対応。
- billing（請求）アカウントをいきなり無効化する。**プロジェクト課金の破壊性が高く、復旧不能・データ喪失につながり得る**（→ [03-cloud-billing-anomaly.md](./03-cloud-billing-anomaly.md) / REQ-218 AC-04）。
- 事実確認前に、利用者へ「漏れていません」「補償します」等を断定する。
- 秘密値・実ユーザーの PII をチャット / Slack / チケット / スクショに貼る。
- 一人で抱えて報告期限を逸する。**迷ったら早めに相談・通報**（公的窓口は無料）。
- 監査ログ（`audit_logs`）だけを根拠に「不正なし」と結論づける。`writeAuditLog` は **fire-and-forget で書き込み失敗が操作をブロックしない**ため、ログが欠落し得る（`src/lib/auditLog.ts:25-27`）。複数ソースで突き合わせる。
