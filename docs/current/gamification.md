# 貢献レベル・バッジ・コレクション — いまの仕様

> 「いま何が正しいか」だけを書く。「そのとき何を変えたか」は `docs/requirements/REQ-*.md`（履歴）。
> 食い違ったら**コードが正**。正本: `supabase/schema.sql` の「貢献レベル / 経験値（XP）エンジン」ブロック

## 何のためにあるか

卒業研究として**参加率と継続率を追跡する**ためのもの。だから「たくさん投稿させる」のではなく、**質のよいデータが集まる方向に効く**ように作ってある。以下の設計判断は全部そこから来ている。

## いいねは報酬にしない

**XP が増えるのは「承認された投稿」だけ。** 未承認・却下・いいねでは一切増えない。

いいねを報酬にすると、いいねを集めやすい投稿（映える写真など）に寄って**データの質と分布が歪む**。指標を目標にすると指標が壊れる、という話（Goodhart の法則）。**この判断を覆さないこと。**

## XP の増え方

承認 1 件につき、基本点＋品質＋初回発見で決まる。

- **不在確認（見つからなかった報告）にも加点する**（+4）。「いなかった」は分布を知るうえで価値のあるデータなので、報告する動機を消さない
- **初回発見にボーナス**（種 +15 / 情報種別 +10 / 市区町村 +12）。まだデータが無い場所・種に向かわせる

**1 日の上限は 120 XP。** 量産で稼ぐ動機を断つ。初回発見ボーナスが自然に減っていく設計と合わせて、同じ場所で反復投稿しても旨味が小さい。

係数は `xp_for_post()` と `xp_daily_cap()` が唯一の正で、`src/lib/constants.ts` 側と同期している。**片方だけ変えないこと。**

## 利用者は進行を書き換えられない

`user_progress` と `user_badges` には **INSERT / UPDATE ポリシーを作っていない**。書けるのは承認トリガー `award_xp_on_approval` と再計算関数 `recompute_all_progress` だけ。つまりクライアントからは読めるだけ。

## 再計算の落とし穴

投稿を消したりデータを整理したあとに `recompute_all_progress()` / `recompute_all_collections()` を回すとき：

- **承認済み投稿を持つ利用者しか UPSERT されない。** 投稿が 0 件になった人の `user_progress` / `user_collection` の行は**残るので手で消す**
- **バッジに剥奪ロジックは無い。** `check_and_grant_badges` と同じ条件で再判定して `user_badges` から手で DELETE する

2026-07-28 にテスト投稿 33 件を消したときに判明した。

## コレクション

承認済み投稿から種ごとの図鑑を作る。3D 表示（three / react-three-fiber）は**「3D で見る」を押したときだけ読み込む**。初期バンドルに入れない（予算を守るため）。
