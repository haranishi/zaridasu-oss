# 調査計画と希少種の記録 — いまの仕様

> 「いま何が正しいか」だけを書く。「そのとき何を変えたか」は `docs/requirements/REQ-*.md`（履歴）。
> 食い違ったら**コードが正**。正本: `supabase/migrations/20261001000001_req330_fieldwork.sql`

調査の日を「計画する → 案内される → 地点ごとに結果を残す」の一続きにする機能。結果は、外来種がいた（公開の投稿）、いなかった（不在の投稿）、希少種がいた（非公開の記録）の 3 種類で残す。コードは `src/features/fieldwork/` にまとめてあり、差し込み口はそのフォルダの README にある。

## 希少種の記録は posts に入れず、公開経路の外の別表に置く

posts から漏れる道は多い。RLS を通らない公開 RPC（集計・ランキング・週報）、誰でも一覧できる写真置き場 `post-photos`、投稿の状態に関係なく全件公開の comments と likes がある。posts に入れれば、そのすべてに除外条件を書き続けることになり、1 か所の書き忘れで生息地が公開される。だから別表 `rare_sightings` と非公開の写真置き場 `rare-photos` に置いている。計画・地点・地点と投稿のつながり（`survey_plans`・`survey_plan_stops`・`survey_stop_posts`）も同じ扱いにした。posts に列を足すと、列単位の GRANT によって anon から見えてしまうからだ。

## 4 表とも、読めるのは本人と管理者、書けるのは本人だけ

| | 本人 | 管理者 | 他人 | anon |
| --- | --- | --- | --- | --- |
| 読む | 自分の分 | 全員の分 | 0 行に見える | 権限なし（42501） |
| 作る・変える | 自分の分 | 自分の分だけ | できない | できない |
| 消す | 自分の分 | 全員の分 | できない | できない |

管理者の判定は private_spots と同じ式（JWT の `app_metadata.role`）。他人の計画に地点を足す・他人の地点と投稿をつなぐ操作は、WITH CHECK の「自分のもの」の条件で止めている。`user_id`・`client_id`・`created_at`（地点では `plan_id` も）は UPDATE してもトリガーが旧値に戻す。

## 地点は座標を複製して持ち、地点を消しても記録は残る

元の非公開スポットを消しても計画は壊れない（`source_id` は外部キーにしていない）。並べ替えは RPC `reorder_survey_plan_stops`（SECURITY INVOKER）が全地点を一度に振り直す。地点を消すと、つながりは一緒に消え、希少種の記録は `stop_id` が空になって残る。

## 希少種の記録は再送しても増えず、写真は自分のフォルダのものだけ付く

種は DB が形式しか検査せず、一覧は `src/features/fieldwork/constants.ts` の 1 か所。端末で作る `client_id` に一意制約があり、再送しても 2 行にならない。写真のパスは `<自分の user_id>/ファイル名` だけを受け付ける。付けた地点が自分のものでない・もう無いと拒否されたら、地点を外して入れ直す（記録は失わない）。

写真置き場 `rare-photos` は非公開・5MB・jpeg/png/webp。表示は 1 時間の署名 URL だけで、公開 URL は作らない。アップロード前に EXIF を消し、消せなければ送らない。**記録を消しても写真の実体は残る**ので、`deleteRareSighting` が返すパスで写真も消す（一部しか消せなければ画面に残った枚数を出す）。**退会では、退会の前に Storage API で `rare-photos/<uid>/` を一覧して消す**（表を消しても実体は残るため）。消せなければ（通信・権限で 0 件・回数の上限）退会を止め、やり直してもらう。進めるのは置き場そのものが無い環境だけ。写真を消したあとで退会に失敗したら「写真は削除済み」と伝える。

## 希少種の保護は「地点の id」でなく「場所」で決める

自分の希少種の記録から **300 m 以内**（位置の規則と同じ距離）の地点・位置から作る投稿は、位置を `hidden` にする。地点の id だけで決めると、「この計画をもう一度使う」（地点の id が新しくなる）・地点の足し直し・別の端末の記録・送信待ちの記録のどれでも保護が外れるため。

- 計画を読むとき・地点を足したときに、地点の周りの自分の記録の座標も取り（緯度経度の範囲で絞り、距離は端末で測る）、控えにも入れる。取れなかった・範囲検索が上限（1000 件）まで返ったときは、その地点を仮の印で守る。地点を外しても記録は落とさない（DB でも stop_id が空になって残り、近くの別の地点を守る）
- 投稿を作る直前にも DB で確かめる（「いなかった」・送信待ちの「いなかった」・「いた」でフォームを開く直前・ピンの「ここで投稿」）。確かめられなければ伏せる側に倒す。**圏外で投稿の下書きに入った「いた」は、下書きに地点の印を持たせ、電波が戻って送るときに確かめ直す**（近ければ非公開。送れたら地点とつなぐ）
- 位置を非公開にする不在の逆ジオコーディングは、座標を小数 2 桁（約 1 km）に丸めて送る。Sentry のパンくずからは URL のクエリ（座標）を落とす
- 後から希少種を記録したら、その記録の地点と 300 m 以内の自分の地点につながる自分の投稿を `hidden` にする（送信待ちの記録は送れた時点で）。非公開化は一方向で、本人は戻せない
- **ほかの利用者の公開投稿は対象外。** 他人は希少種の記録を見られないので、要件の範囲外とした

## 上限は管理者には効かない

| 対象 | 上限 |
| --- | --- |
| 計画 | 直近 24 時間で 30 件・1 人 1000 件 |
| 地点 | 1 時間 300 件・1 計画 100 か所 |
| 希少種の記録 | 1 時間 60 件・1 人 5000 件 |

超えると P0001 で止まり、画面は DB の文言でどの上限かを分けて出す（`lib/errors.ts`）。投稿の上限（24 時間 5 件）は変えていない。不在の投稿も 1 件に数える。

## 「いなかった」は審査に回り、二重になる隙が 1 つ残る

不在の投稿は種ごとに 1 件・調査方法 structured。**管理者以外の投稿は `protect_post_insert_columns` が `pending` にするので、運営の確認のあとで公開される**（画面にもそう出す）。そのまま公開になるのは管理者の分だけ。

posts には送信を見分ける鍵が無い。作れた投稿の id は送信待ちに書き残し、途中で上限などに当たっても残して、押し直しで作り直さない。**ただし、投稿が作られたのに応答だけが届かなかった場合は、送り直しで二重になる**（既知の制約。今回は防がない）。

## 画面: 入口は地図の「調査」ボタン 1 つで、記録は地点シートで終わる

- **パネル**: スマホは下半分、PC は地図の右。開いている間は右下の「調査 N/M」を隠す。計画タブは上から、題名と進み具合（「N / M地点 終了（飛ばしを含む）」）→ **次の地点のカード**（今日の計画で未調査の地点があるときだけ。パネルで唯一の塗りつぶしのボタン）→ 残りの地点をまとめて案内（開閉）→ 地点の一覧 → 地点を足す → 計画の操作 → これまでの計画（1 件以上のときだけ）
- **計画を作る**: 計画が無いときは「調査の計画を作る」。前の晩に作る使い方に合わせて予定日を選べ、16 時以降は明日を選んでおく。予定日が明日の計画は「明日の計画」と出す。「地図で選ぶ」は、スマホはパネルが帯になり、PC は地図の下端に同じ帯を出す（Esc でも終わる）
- **経路ボタン（Google・Yahoo!・Apple）は地点シートにだけ置く。** 地点シートは毎回安全の一言を通るので、安全の一言を通らない入口を作らない。まとめて案内は 4 地点ずつに分け、開いた中に安全の一言を出す
- **地点シート**: いた（投稿フォーム）・いなかった（確認 1 回）・希少種を記録・飛ばす（理由は任意）と「元に戻す」。位置は、現在地が誤差 100 m 以内かつ地点から 300 m 以内なら現在地、それ以外は地点の座標。どちらを使うかと理由を確定前に 2 行で出し、その箱の高さは最初から取っておく（位置が更新されてもボタンが動かない）。距離は「約60m」「約2.8km」の形で、数と単位を行またぎさせない
- **「希少種あり」の印は「希少種を自分の地図に表示」を入れたときだけ**（一覧の札・番号の錠前・「希少種 N」・地図の印）。既定は出さない（画面写真から生息地が漏れないように）。入れている間は紫の帯を出す（スマホは地図のすぐ上に差し込んで地図を下げ、印を隠さない。PC は地図／写真の切り替えにそろえて重ねる）。保護（位置の非公開）は表示に関係なく効く。**地点シートには非公開の固定を示すものを何も出さず**、「いた」のフォームと「いなかった」の確認の中でだけ「この地点の記録は、位置を公開しません」と出す
- **確認のボタンの並びは「左＝やめる・右＝実行」**（削除・計画を終える・地点を外す・破棄・ログアウト前の確認など、すべて）
- **語の途中で折らない**: パネルとシートに `word-break: auto-phrase` と `text-wrap: pretty`。長い種名は翻訳文に折ってよい位置（ゼロ幅スペース）を入れてある。BudouX の JS は入れていない

## 端末に残すものは利用者ごとに分け、ログアウトと退会で片付ける

計画の控え（localStorage）は「最後に同期した内容」として圏外で見せ、編集は止める。いなかった・飛ばす・元に戻す・写真なしの希少種は送信待ちに積み、online・パネルを開いたとき・画面を開いたときに送る。送る直前に送信待ちを読み直し、別の送信が送り終えた項目は送らない。送れない項目は理由と「破棄」を出す。

ログアウトでは控えと投稿フォームの下書きを消す（どの経路の SIGNED_OUT でも）。送信待ち・圏外の投稿の下書き・圏外で保存した非公開スポットが残っていれば、件数を見せて確認を出す（送ってからログアウト／破棄してログアウト／やめる）。非公開スポットは座標が入るので、送るか破棄するまで端末から消さない。送るときはほかの送信が終わるのを少し待ち、送れなければ圏外か上限などかで文言を分ける。ログアウトに失敗した（トークンが切れたまま圏外でセッションが残った）ら false を返して何も消さず、破棄はログアウトできてから行う。確認を出している間の 2 回目の signOut は 1 回目を待つ。退会では送信待ち・控え・下書き・圏外の投稿の下書きを全部消す。正本: `src/context/AuthContext.tsx`・`src/features/fieldwork/lib/localData.ts`

## 公開経路に出ていないかは CI が見張る

`npm run private-tables:check` が、schema.sql と migrations から 4 表に触れる関数を集めて許可リストと突き合わせ、4 表を参照するビューと、公開の経路のコード（`supabase/functions`・`src/app/api`・`src/app` の route.ts）に 4 表と `rare-photos` の名前があれば落とす。権限と制約は pg-tap（`supabase/tests/rls_req330_fieldwork.sql`）が確かめる。署名 URL や大きさの制限など storage API 側の動きは CI では確かめられない。
